# 桌面端交互规范：会话与 agent 的连接生命周期

范围：一个会话怎么跟它的 agent 连上、什么时候连、连不上怎么办。
配套：`docs/modes-spec.md`（模式）、`docs/permissions-spec.md`（权限请求）。

---

## 1. 无感启动（2026-10-21 拍板）

**旧行为**：每次开应用都要先进设置页、点一下「连接」，连上之前所有会话都跑演示数据。
这不是正常产品该有的手感。

**新行为**：连接跟着会话走，不跟着应用启动走。

### 1.1 触发点

| 时机 | 是否自动连 |
|---|---|
| 侧栏点开一个会话 | 是 |
| 切到一个会话标签 | 是 |
| 在会话里发消息 | 是（保底：前面的触发可能被跳过） |
| 新建会话 | 否（还没有归属 agent；发第一条消息时连） |
| 打开设置页 | 否（那里是显式操作，不是使用路径） |

### 1.2 连谁

会话自己的归属优先：`session.profileId`。没有记录（老会话）时退回当前选中的连接。

### 1.3 并发

同一个 profile 同时只允许一个 connect 在飞。自动启动和设置页手动点可能撞在一起，
两个 `agent_connect` 会让后端 kill 掉刚起的进程 —— 后到的那个调用必须复用先到的 Promise，
而不是再起一次。

### 1.4 失败

- 不弹模态框，不打断用户；把失败原因写进**那个会话的消息流**（system 消息），
  用户看得见是哪一步坏了。
- `profiles.connected` 保持 `false`，下次再触发会自动重试。
- 设置页仍然是看详细错误的地方（那边保留逐 profile 的错误行）。

### 1.5 断开

manifest 上不做自动断连：进程随应用退出。用户主动「断开」后，`sessionsByProfile` 里
该 profile 的记录被摘掉，下次打开会话又会自动连 —— 这是刻意的：断开是「现在别连」，
不是「永久别连」。

## 2. 会话列表标「归属」，连接状态放标题栏

两件事必须分开呈现，否则同一段信息在两处打架：

| 信息 | 位置 | 形态 |
|---|---|---|
| 这个会话属于哪个 agent | 会话列表条目尾部 | 连接名小徽标，**中性色**，不带状态语义 |
| 这个会话现在连没连上 | 会话标题栏右侧 | 连接名 + `已连接` / `未连接`（绿/灰） |

- 列表里不做连接状态着色：一列会话会变成一堆绿灰点，看不出重点，而且用户会误以为
  徽标本身是状态灯（2026-10-21 实测反馈）。
- 没记 `profileId` 的老会话不显示徽标，不写「未知」这种噪音。
- 标题栏断开时给一句「打开会话会自动连」，把无感启动的行为就地说明。

## 3. 左下角不再放 Agent 列表

连接是从会话进去的，左侧常驻一份「Agent 列表 + 连接点」属于两套入口。移除，
只保留「设置」按钮。想断连、想改默认模式、想看握手结果，都去设置页。

## 3.5 新会话选 agent：主按钮 + 下拉，不做「建完再改」

- 主按钮：用**最近用的那个连接**新建（单连接用户零步骤、无额外控件）。
- 只配了 2 个以上连接时，主按钮右侧才出现下拉箭头，列出现有连接，
  选中即用那个连接新建。一个连接时连箭头都不渲染。
- 不做「先建会话、再去标题栏改归属」：那是把一件事拆成两步，而且用户往往先发了一句话
  才发现归属不对。归属必须在会话诞生那一刻就确定。
- 不做「每次新建都弹选择器」：单连接用户被迫点一次无意义的下拉。
- 空会话阶段归属仍可改（标题栏），但那是补救入口，不是主流程。

## 3.6 标签：自动打开一次，关到底就留空态

- 启动后会话列表回来时，自动打开最近一个会话 —— **只做一次**。
- 用户把标签一个个关到底，就是「什么都不开」：主区显示空态（`WorkspaceEmpty`：没有打开的标签 + 新建入口），
  **不自动补开一个**。
- 机制：这条自动打开曾经写在 `useEffect([sessions, tabs.length])` 里、判据是 `tabs.length === 0`，
  于是关掉最后一个标签的瞬间它又开回来 —— 表现为「标签无法全部关闭」（2026-10-23 报的 bug）。
  自动行为必须一次性（`autoOpenedRef`），不能跟着「当前是不是空」反复触发。

### 聊天区渲染哪个会话，唯一依据是「激活的标签」

- 关掉当前标签后，聊天区**必须跟着换到相邻标签的会话**；标签条高亮换了、聊天区还停在被关掉的那个，
  是同一件事没说清（2026-10-25 报的 bug）。
- 机制：`lastSessionId` 是 `activeTabId` 的**派生值**（`sessionIdForActiveTab`），
  `closeTab` / `closeSessionTabs` / 列表剪枝 / `selectTab` / `openTab` 五条路径不必各自记得改它。
- 三种情况要分清：激活的是会话标签 → 切到它；激活的是设置/项目/PR 标签 → **不动**；
  一个标签都不剩 → **清空聊天区**（回到空态）。用「不动的 null」和「清空的空串」区分，别让一个 null 兼两义。

## 4. 验收

1. 关掉应用重开，直接点一个会话 → 不用去设置页，消息能正常发出去。
6. 配两个连接时：主按钮直接建（继承最近用的），箭头下拉里选另一个则用它建；
   只有一个连接时箭头不出现。
2. 新开一个会话、直接发消息 → 自动连上并回复。
3. 把 profile 的 program 改成不存在的命令，点开会话 → 该会话消息流里出现失败原因，
   应用不卡、不弹模态框。
4. 同一 profile 连点两个会话 → 日志里只有一次 `agent_connect`。
5. 设置页手动断开后，再点会话 → 又自动连上。

## 5. 删除会话

入口：会话条目右上角，**悬停**才出现的 `⋯`。菜单里目前只有「删除会话」。
不放常驻垃圾桶：删除是低频、破坏性的操作，不该一直挂在那儿等误点。

三条已定的语义（2026-10-21 所有者拍板）：

1. **只删本软件里的**：本地会话行 + 它的全部消息 + 群成员关系。
   **agent 那一侧的会话不动** —— 用户还能在别处接着用。确认框里必须写明这一点，
   否则用户以为把 agent 的记忆也清了。
2. **正在跑一轮的会话不许删**：客户端还没有 `session/cancel`（E3.1 未做），
   删掉会留下一个还在跑、没人看的 agent。菜单项禁用，理由写在菜单底部。
3. **一次明确确认，不兜底**：不做回收站、不做宽限期 —— 授权即最终。
   确认框的责任是把后果说准（删什么 / 不删什么 / 能不能恢复），说清就照办。

删除失败时**留在确认框里说原因**，不弹系统 alert，也不关框 —— 没删成不能让人以为删了。

## 6. 批量管理：暂不做

会话多起来之后，「一条条删」确实会变成 2N 次点击 + N 次确认。但批量删除是破坏性放大器，
而我们现在连撤销都没有，所以先不做，理由记在这里免得反复讨论：

- 现状：会话按「今天 / 昨天 / 更早」分组，常见规模远没到需要多选的程度；
- 真要做的时候，做法是**多选模式**（顶部「管理」→ 条目出现选择框 → 底部条显示「删除 N 条」→ 二次确认），
  **不做**「一键全选并删除」，也不做「清空更早」这种按组秒删；
- 触发条件：会话数经常超过 30 条，或用户明确提出要按时间批量清理。到那时再上。

### 历史消息：只写界面不落库 = 丢历史

- 用户消息、agent 回答、**系统提示**（连接失败 / 这一轮失败 / 发送失败 / `@` 不到人 /
  没有连接配置）全部要落库，`role` 分别是 `user` / `player` / `system`。
- 只在内存里提示的后果实测过：恢复会话后看到「连着五条我的消息，中间一条回复都没有」，
  既看不出是失败了还是回答丢了。
- 回答落库的消息 id 必须**每轮唯一**（`stream-${acpSid}-${时间戳}`）。曾经用
  `stream-${acpSid}`，而写入是 `ON CONFLICT(id) DO UPDATE`，后一轮直接把前一轮覆盖掉。

### 事件路由：归属是后端的会话记录，前端不猜

这条是重构后的规则（之前是前端维护「ACP 会话 → 界面会话」映射，并在缺失时退回
`lastSessionId`，切一下会话消息就串到别的会话里，库里也跟着错）。

- 后端 `SessionRecord` 带 `ui_session_id` 与 `author_id`：
  `agent_connect(profile, uiSessionId)`、`session_new(..., uiSessionId)`、
  `session_load(..., uiSessionId)`、`session_prompt(..., uiSessionId)` 都会写这份记录；
  `session_prompt` 以**这一次是谁发的**为准覆盖归属（同一成员会话可被不同群 @）。
- **每个**出站事件（`notification` / `request` / `promptStarted` / `promptResult` / `promptFailed`）
  都带 `sessionId`（ACP 会话）、`uiSessionId`（该投给谁）、`authorId`（发言的群成员）。
- 前端只用这三个字段：能投就投，缺失就丢弃并记 `DROP-NOMAP` / `RESULT-NOUI` 日志。
  **禁止**再用「当前打开的会话」补归属 —— 用户切页面不该改变数据的归属。
- 设置页为成员新建会话这一类「不属于任何界面会话」的连接，`ui_session_id` 就是 None，
  其事件不会投给任何人（记 `BIND-NOUI`）。

### 重放的历史不是新回答

`session/load` / 重连之后，agent 会把上一轮**重放**成 `agent_message_chunk`，和真回答一模一样。
客户端只把「自己发起的那一轮（`promptStarted` 之后）」的 chunk 当回答；没有这个标记的
一律记 `DROP-REPLAY` 丢掉 —— 那些内容库里已经有了，再收一遍就是重复。

### 切会话必须重读历史（合并不是覆盖）

打开某个会话时总是读一次库，把结果与内存合并：库里有的以库为准，内存里不在库里的
（正在流式、刚发出还没落库的）接在后面。以前「内存非空就不读库」的守卫会让
之后再落库的内容在界面上永远不出现（实测：最后一条回答看不到）。

## 7. 设置页：列表 → 详情（2026-10-23 拍板，替代原来的单列长滚动）

原来一页里塞了连接（≈450 行，每个连接一整套表单）、成员（内嵌 AgentUsers）、偏好、诊断事件流，
导航只是锚点 —— 连接一多页面就线性变长，偏好被埋在最底下。现在按「资源」与「偏好」分开。

### 7.1 四个分区

| 分区 | 形态 | 内容 |
| --- | --- | --- |
| 连接 | 列表 → 详情 | 列表是卡片（名称 / launch 方式与目标 / 状态点，三行内）；详情含主机、端口、账号、认证方式、私钥、密码、agent 命令、工作目录，以及探测、发现候选逐条验证、路径历史 |
| 成员 | 列表 → 详情 | 列表是成员行（头像、名字、profile、状态）；详情是现在 AgentUsers 那套表单 |
| 群聊 | 行内设置项 | `@ 玩家时附带最近几条记录`（0–20，默认 5）+ 现有两段说明与超量警告 |
| 外观 | 行内设置项 | 主题三档 |

- **会话分区删除**：三条全是「未接线」占位，看起来像设置其实没接线，是最糟的一类。
- **诊断移出设置**：入口在状态栏「轨迹」键**旁边**（所有者 2026-10-23 定），浮层里显示 agent 事件流 + 复制。
  设置读取时遇到的脏值也进这个事件流（后端同时写日志）——**不阻塞启动，但绝不静默**。
- 日志落 `app_data_dir/logs/sincearc.log`（同时写 stderr，超 5MB 挪成 `.log.1` 留一代）。
  桌面应用双击启动时没有终端，只写 stdout 的 `tracing::warn!` 等于没记录。
- 行内设置项：label 左、控件右，**不占整行宽度以外的额外容器**；同一分区内的项之间用分隔线，不再一项一个边框盒。

### 7.2 动线

- 详情页全宽替换列表（不并排、不开抽屉：抽屉是玻璃叠玻璃，边界糊）。
- 顶部 `← 返回`；`Esc` 等同返回；**返回后焦点回到进来的那一行**（兜底：那一行已不存在则聚焦列表首行）。
- 分区切换时回到该分区的列表（不记忆子页），避免"从设置再进来就是某个连接详情"这种意外。

### 7.3 落库

设置必须持久化（所有者 2026-10-23）：现在页脚写着「仅本次运行有效」，用户点进详情改完会以为存了。

- 存储：与 profile 同一个 SQLite，单表 kv（`settings(key TEXT PRIMARY KEY, value TEXT NOT NULL)`）；
  键名常量集中一处，前端不拼字符串。
- 读：启动时加载一次；**读不到就用默认值，不阻塞界面**。
- 写：改动即时保存（防抖），**写失败必须回报界面**（不许静默吞掉——那等于让人以为存了）。
- 不认识的键：忽略并保留原值（兜底规则：将来加/减字段不能让老库打不开）。

### 7.4 连接的草稿与探测门槛

连接的新建与编辑都走**草稿**（所有者 2026-10-23）：点「新建连接」只在界面建一份草稿，
**不进 profile 数组、不落库**；点「保存」才写入。理由：草稿一旦落库，就会出现在
「新建会话」的连接下拉里，一条从没连通过的配置能被选中，这是缺陷而不是小毛病。

- **只要新建就保证可用**：保存按钮的可用性挂在**当次探测结果**上，探测没通过不许存；
- 改任何字段 → 上一次探测结论作废（参数变了，结论就不作数），跟成员表单同一套纪律；
- 保存不可用时**必须写明原因**（`还缺：主机、用户名` / `先探测通过才能保存`），不许只灰着；
- 「连接 / 断开」只对已保存的连接出现，草稿没有已保存身份；有未保存改动时禁用并写「先保存再连接」；
- 丢弃草稿（返回列表、切分区、Esc、关设置）**要确认**：这些改动没保存，丢了就没了；
- 发现结果走同一条路：组装成预填值 → 建草稿 → **自动跑一次探测**，用户点完就能看到结论，而不是再点一次。

## 8. 会话打不开时：居中的错误态，不是横幅（2026-10-24 拍板）

「连不上」有两条入口，过去给了两副面孔：打开会话失败是一条 10px 的等宽灰药丸塞在消息流里（而且不落库，
切走就没了），续不上（resume unavailable）是浮在消息区上方的玻璃横幅。同一件事两种形态，且最该被看见的那条
反而最安静。现在统一成**一块居中的错误态**。

**形态**：复用 `ui/EmptyState`（logo 磁贴 + 标题 + 说明 + 操作），与空列表页同一族：
- 图标：`size-12 rounded-card border border-line-1 bg-surface-1` 里的 `BrandMark size-7` —— 与空态同一份，
  **不给标识染警示色**（标识是品牌，不是状态色；它一旦变黄，就不像 sincearc 了）
- 标题：`连不上这个会话`
- 说明：`<错误码> <原因>`，等宽、可换行、两行以上截断并 `title` 全量
- 操作：主「重试」；`resume.unavailable` 时次「新建会话」；连接类错误次「打开设置」
- **整块不染色**：标题用 `ink-1`，与空态一致。一套单色主题里给错误态刷黄，会把「品牌标识 + 主标题」
  一起拖进警示语义，既抢眼又不属于这套语言；「这次没连上」由状态栏的 `连接失败` 与这块的存在本身表达。
  `danger-1` 仍然只留给数据损坏与破坏性操作的确认。
- **重试要有可见的进行中**：按钮转圈 + 文案换「正在重连…」，标题下方一条 2px 的不定进度细条
  （`.sc-indeterminate`，跑道 `--s2`、滑块 `--a1`，1080ms）；重试期间其它按钮禁用，防连点。
  `prefers-reduced-motion` 下把两条动画都放慢到 2.4s（不取消，保留"还在动"的反馈）。

**落点按有没有历史分两种，视觉只有一份**：
- 会话没有历史（`msgs.length === 0`）：错误态**占满消息区**，替换掉空态提示 —— 这时没有消息流可看，
  也就不该假装有
- 会话有历史：错误态**接在最后一条消息之后**（打开即滚到底，正好落在视口内），历史照常在上方保留。
  不许整块盖掉：「连不上 agent」不等于「这些消息不存在」，盖掉会让人以为会话被清空了

**不落库**：它是「这次打开的结果」，不是历史。每次打开都会重试，结果实时替换这一块；落成 `role=system`
消息会在历史里留下假条目，重试成功还得回头删。与之相对，**发消息时的失败仍然落库**
（`pushSystemNotice`，那是这一轮的真实记录），这条规矩不变。

**「续不上」只有一个面孔**（2026-10-24 补）：它由这块错误态 + 状态栏表达，
**不许**再往消息流里写一枚「续不上：…」的药丸 —— 发送时自动连接才发现续不上，也一样，
只把会话的连接态标出来（`reportResume`）就够。踩过的坑：E13.7 在发送路径里加了那枚药丸，
随后这块错误态落地时没人回头删，于是同一件事两个面孔，而药丸会落库、重开会话后仍在历史里。
守卫：`src/lib/notice-guard.test.ts`（扫 `pushSystemNotice` 的文案里出现「续不上」就红）。
成员会话恢复不了是另一回事 —— 主会话是好的，那就是一次真实的发送失败，落库并写明「这一条没有发出去」。

**成功即消失**：连接成功时这块什么都不显示，不留「已连接」的痕迹 —— 正常状态不需要装饰。

**状态栏三态**，不许拿近似档顶：
| 状态 | 点 | 文案 | 含义 |
| --- | --- | --- | --- |
| connected | `ok-1` 实心 | 已连接 | 这一轮握上手了 |
| error | `danger-1` 实心 | 连接失败 | 最近一次尝试失败（`connectError` 有值） |
| untested | 描边空心 | 未连接 | 还没试过，或已主动断开 |

三态必须能区分：只有 `未连接` 时用户不知道「要不要点一下试试」，只有两个状态时「还没连」和
「连不上」长得一样 —— 那正是这条被报上来的原因（「连接失败就是静默失败，有点隐秘」）。

## 9. 首次打开会话：先顶骨架屏，不留空白

打开会话有三段等待叠在一起：读本地历史（库大或走 `/mnt/c` 的 9p 挂载会明显变慢）、无感连接 agent、
拿 usage。过去这段时间就是纯空白 —— 既不像「空会话」，也不像「在加载」，慢一点用户只会怀疑卡住了。

**过渡要覆盖「打开 → 可用」整段，不是只等历史**：可用 = 历史读回 **且** agent 握上手。两段都完成之前
都算打开中（`opening || connectPending`），否则会出现「骨架消失、消息空着、其实还在连」的半成品状态 ——
那正是「静默加载」剩下的那一半。

**形态**：`ui/EmptyState kind="loading"`（三条骨架条，`--s2`）+ `aria-label="正在打开会话"`，占满消息区、居中；
与错误态、空态共用同一块位置，视觉上属于同一族。

**有缓存消息时不用骨架遮内容**：这类会话切回来时消息立即可见，遮住反而更慌；过渡改由状态栏的
`连接中…`（`Badge status="connecting"`，`accent-1` 脉冲点）承担，直到真正连上才变「已连接」。

**只在「真的什么都没有」时出现**：`msgs.length === 0 && opening`。已经有缓存消息的会话（切回来）不显示，
否则会把内容盖成一屏骨架 —— 那一瞬比空白更让人不安。

**要有阶段说明**：骨架条下面一行 `text-caption ink-3` —— 「正在读取会话历史…」/「正在连接 agent…」。
冷启动时连接可能要几秒，只有几条在跳说不出在等什么；两个阶段分开写，用户才知道卡在哪一半。

**快的时候不该出现**：原语自带 300ms 延迟（`showLoading` effect），本地库毫秒级返回时用户看不到任何闪烁。

**优先级**：连接错误态 > 骨架屏 > 空态 / 消息流。连不上时不必再假装在读历史。

## 10. 自动同意：只在输入区，档位摊开可读

审批有两道闸（见 `docs/acp-notes.md`「审批两闸」）：状态栏那个 `ModeSelect` 是**上行**——改 agent 的
审批档，让 agent 少问；这里的自动同意是**下行**——agent 已发来的请求，客户端替你答。两者都改变
「被打断几次」，所以位置必须分开，否则用户会当成同一个开关的两段。

**位置**：输入区工具条右侧，与发送/附件同一行。理由：它管的是「发出去、答回来」这个动作区
（与 E15 的分区原则一致：消息区说内容、输入区说可用性）。状态栏保持原样，不并列两个审批概念。

**形态是「当前值 + 菜单」，不是开关也不是分段**（2026-10-24 定）：

```
收起    [自动同意 关 ⌄]  —— 一枚紧凑触发器，只说当前是哪一档
展开    关             agent 每次提问都交给你决定              ✓
        编辑类         改文件 / 删除 / 移动替你答；命令与读取仍交给你
被覆盖  整枚置灰不可点（agent 档为 accept_edits / dont_ask），title 写明「本来就少问，这道闸不起作用」
```

### 开关与分段的两条硬性规则（2026-10-25 定）

**开关（两态）**：轨道是一块平的 `surface-3` + `--control-border`，**不整片点亮**。
开/关只由两处表达：圆点在左还是在右、圆点是 `ink-3` 还是 `ink-1`。
拿强调色填满整条轨道会变成一块白板（暗色主题的 accent 本身就是浅灰近白），
与「底层平铺 + 圆角边框」的语言冲突 —— 实测就是「一开整块变白」。
圆点必须写死 `left/top`（`left-px top-px`）：只写 `absolute` 时按钮默认
`text-align: center` 会把无定位的绝对子元素摆到居中位置，于是 off 也贴右、
on 直接溢出控件（实测 off=18px、on=32px 越界 12px）。

**分段控件的滑块**：首帧不许补间。滑块量到真实位置前是 `width: 0`，
而 `.sc-switch__thumb` 带 `transition: width` —— 于是每次页面初始化都会
「从零宽长到占满」。首帧画完（`requestAnimationFrame`）再开补间；
之后用户切换档位仍要滑。

为什么不是开关（自动同意那一项）：开关只有两态，加到第三档就变成「点一下循环到下一档」，用户猜不到下一次是哪档 ——
而这恰好是「替用户放行什么」这种必须显式的作用域。
为什么不是分段：它长在输入工具条里、紧挨发送键，而分段在语义上是**表单里的单选项**，
视觉上像一排小标签页；两个 1 字标签加滑块又不是自带名字的选项，离开「自动同意」前缀就读不通，
窄窗时前缀一藏就只剩两个光秃秃的框。一个很少改的安全设置，不该在工具条里占一排按钮、还是最重的那个元素。
菜单还能给每档配一行说明 —— 这是唯一讲得清「这一档替你放行什么」的地方，分段与开关都放不下。

**设置页那一项仍是分段**（`设置 › 群聊`）：那是表单行，两档并排、都在视野里，场合不同，不必强行统一。

**任何形态下都不用原生 `<select>`**（规范禁用，`native-control` 会红）；要做下拉就复用 `ui/Menu`
（锚定定位 + 键盘 + 点外关闭 + portal）。

**设置页**：设置 › 群聊 ›「新会话默认自动同意」（关闭 / 编辑类），默认关闭。
它**不**与「默认文件编辑审批」并排 —— 那一项在连接里，是 agent 自己的审批档（上行）；
这里是客户端应答策略（下行）。并排会把两闸混成一个概念。
语义是"新会话开始时那枚分段的初始态"，不是持久授权 —— 会话内仍可随时切回关闭。

**文案红线段**（与 §8 一致）：
- 不给它染警示色；它不是一个危险开关，是一个可见、可收回的便利开关。
- 需要说明风险的地方只有一处：`自动同意 · 全部`（若将来做）必须显式标注「包括执行命令」。
- 自动放行必须进轨迹（`permission_decision`），不许只在本地内存里发生。

### 派活在消息流里必须有两半

只有回应、没有开头时，用户看到一条成员发言会问「这回答从哪来的」。所以：

- **发起行**：后端在 `delegate_task` 里与轮次一起写进 `messages`（`role = "user"`、`kind = "delegate"`、
  `payload.delegate = { handleId, targetMemberId, targetName, context, reason }`，正文就是任务原文）。
  **渲染成引用条，不是用户气泡**（2026-10-24 定，仿 IM 的引用回复）：左侧细线 + `SendHorizontal` + 
  「派活给 X · 只带任务描述 · 成因」+ 任务首行（点击展开全文，**展开只改「看不看得全」，不改字号** ——
  点一下字变大，整条内容会像在跳）。它替代「一条用户气泡 + 一条回答」里的前者，
  所以不额外占行，而滚动到回答时仍然看得见「它在回应什么」。
- **为什么落库仍是独立一条**（不能只存在回答里）：① 失败/超时没有回答，引用块就无处可挂，
  指令条要能自己留在时间线上并写「这条派活没成功：原因」；② 重开会话要能看到任务原文；
  ③ 一条指令将来可能对多条回答（中间结论 + 终稿、或多成员跟进），每条都该对上同一条指令。
- **与 `quoted`（引用 PR / issue / 文件）分开**：引用条视觉可以复用，但来源必须是两个字段 ——
  `quoted` 是外部对象（`GitPullRequest` / `FileText` 那套图标），`delegate` 是指令（`SendHorizontal` + 目标人 + 档位）。
- **回应行**：子任务回答照旧以目标成员署名出现在同一条时间线上，紧跟在指令条之后（引用块就是它的抬头）；
- 轨迹里那一步（`delegate` / `delegate_result`）是**事件**，消息流这两条是**对话记录**，两者不互相替代。

  高 28、图标 13、文字 `text-caption`。

不做 `/delegate` 语法、不做工具栏按钮 —— 派活是「对某个人」的动作，入口就该长在那个人身上。

- 父会话轨迹立刻出现一步「派活给 Kimi · 只带任务描述」，进行中；
- 消息流出现这一轮：「→ Kimi：<任务前 200 字>」（后端开的那一轮，`author_id` 是用户）；

- `delegate_wait` 超时（120s）**不弹错误、不取消**：这一步继续显示进行中，附一行「还在跑，没有取消」，

- 打开菜单/对话框时不懒握手，从没连过的 profile 就显示「档位未知」，按只带任务描述派；
- `delegate_wait` 超时后没有那一行「还在跑，没有取消」—— 现在只让轨迹那一步保持进行中。

**文案红线段**：

- 「只带任务描述」不是错误，用 `ink-3` 陈述，不染警示色、不给图标；
- 只有真失败（`50700/50701/50702/50703/50704/50300`）才写失败原因，且原因要按码翻译成人话
  （例：`50300` → 「Kimi 的连接没连上」），不把错误码丢给用户；
- 对话框是浮层，按 §3.4 用 `sc-glass`；成员菜单本体仍是 `.sc-pane`（扁平 + 1px 边框），不换材质。

## 12. 移出成员不改写历史（2026-10-24 定）

「成员被移出群」与「他没说过话」是两件事。移出只删 `session_members` 那一行，`agent_users` 还在，
所以历史消息的身份是**能解析回来的**，不需要隐藏消息，也不需要给消息做快照。

```
消息里的 authorId → 本群成员        → 正常渲染
                 → 全局成员（已移出）→ 头像 / 名字 / 颜色照旧，名字后标一枚「已移出」
                 → 谁都不是（彻底删了）→ 灰底首字母 + 名字「已删除的成员」
```

- **不隐藏消息、不灰掉正文、不染警示色**：消息是当时的事实，「已移出」是一枚 `text-micro text-ink-3`
  的标记（配 `UserMinus` 10px），不是状态色；
- **轨迹泳道用同一份解析**，否则会出现「消息里有名字、轨迹那条支线没名字」；
- **右侧成员竖栏只列在场成员**（`!removed`）：竖栏回答的是「谁在这个群里」，
  已移出的人不该继续占一个头像 —— 否则移出后头像还在，看起来像没移成功；
- **不做写时快照**：反查 id 是同一份真相；快照会变成第二份，成员改名后对不上。

## 13. 能力面板：可以长，但不能被裁掉（2026-10-25 定）

agent 报上来的东西数量不由我们控制 —— 真机 hermes 一次报 16 条命令，面板直接顶出视口，
底部既看不见也滚不到。规矩：

- 面板有个**高度上限**（`min(70vh, 34rem)`），标题行固定；
- **左右两栏**（2026-10-25 改）：左栏是协议能力（`w-52`、单列），右栏是命令列表，
  两栏各自滚动 —— 能力是固定十来项、命令数量由 agent 决定，把它们塞进同一个滚动区，
  看命令就会把能力滚走；
- 两栏之间一条 `w-px` 色块（`line-1/60`），不用 border；
- **没有命令时右栏整栏不渲染**，面板回到 `w-80` 单栏（没有就不出现，不留空栏）；
- 命令描述**单行截断**：描述是补充信息，不该把面板撑宽撑高；
- **CLI 能力块从界面移除**（归档，见 `docs/acp-notes.md`）：那一栏是「预览未接线」，
  留着等于在界面上摆一排点不动的按钮；
- 判定标准只有一条：**任何内容量下，最后一项都必须能滚到、能看见**。

## 14. 流式补间：显示长度追着到达长度走（2026-10-26 定）

问题不是「字来得太快」，是**来得不匀**：后端已按 30ms / 4KB 合批（`src-tauri/src/coalesce.rs`），
前端每段直落界面，于是一屏里会出现 `+45 字 / +17 字 / +44 字 / +9 字` 这种突发 —— 看起来像「往外崩字」，
不像在写。补间要做的是把「到达曲线」抹平成「显示曲线」，不是让字变慢。

**两个长度要分开，且只有一个是真值**：

- **到达长度 `L_arrive`** = `message.text.length`。库、轨迹、复制、turn 摘要都认它；它是一段回答的唯一真值。
- **显示长度 `L_show`** = 渲染时的截断位置。它只影响这一屏，不落库、不进 store、不进日志正文。

**R1 补间只活在渲染层。** 数据面（`useAcpEvents` 的 flush、`messagesAppend` 落库、轨迹面板）一律不动，
读的仍是 `L_arrive`。补间层出来的数字不许回写任何持久状态 —— 否则「显示到哪」会变成第二份真相。

**R2 显示长度永远 ≤ 到达长度。** 绝不预支还没到的字：把「显示进度」当 agent 的真实进度是撒谎，
网慢的时候用户会以为 agent 写完了、其实还在路上。

**R3 速度律是「比例 + 地板」，不是固定速率。** 固定 16ms/字 会让长回答的末尾像卡住（末尾往往剩几十字，
匀速要好几秒）。取

```
gap   = L_arrive − L_show
speed = max(MIN_RATE, gap / TAU)          // 字/秒
L_show += clamp(speed * dt, 1, gap)        // 每帧至少 1 字，且不越过目标
```

`MIN_RATE = 120 字/秒`、`TAU = 0.12s`，两个常量只写在 `src/lib/text-tween.ts` 一处。
读数：差 45 字 → 375 字/秒（约 0.12s 追平）；差 10 字 → 地板 120 字/秒（约 83ms）。
**每帧至少推进 1 字（向上取整）**：否则只剩 1~2 字时浮点推进可能停在原地，末尾看起来又卡住了。

**R4 收口：正常结束走有界追帧，停止 / 出错一帧拉满。** 用户点停止（消息标 `stopped`）或本轮出错
（`promptFailed`）时，在**同一帧**把 `L_show` 拉到 `L_arrive` —— 这两种情况用户要立刻看到「停在哪、错在哪」，
不许再有动画。正常结束（`end_turn` 一类）则允许继续追帧，但受两个约束同时管：

- **按剩余时间配速**：`delta = ceil(gap × dt / 剩余时间)`，`SEAL_BUDGET = 600ms` 从收口那一刻起算；
- **每帧不超过 `SEAL_RATE_MAX = 3000 字/秒`**（约一行），免得大段一次糊上去；两个约束冲突时**截止优先**：
  剩余时间 ≤ 0 的那一帧直接拉满（极端大块仍会跳，这是刻意的 —— 宁可在 600ms 内收干净，也不让界面比状态栏慢半拍）。
- 收口后的追帧**不用** R3 的速度律：`gap / TAU` 会让任何差距都在 ~120ms 内走完，等于又变成闪。
（2026-10-26 修正：原口径是「收口一帧拉满」，见下面的取证。）

**为什么改（真机取证）**：agent 最后一条消息是**整块到达**的，且与轮结束几乎同帧。实测两轮分别是
「20 个 6–34 字的分片（间隔 31ms，正好是后端 coalesce 节拍）+ 最后一发 332 字」和
「渐进到 269 字 + 最后一发 1383 字（占全文 84%）」。旧口径下这一大段没有任何可动画的时间窗口，
视觉就是「一下蹦出一段」。600ms 摊开约等于**每帧一行**，读作「快速写完」。

**这条的代价，写在这里备查**：全文最多晚 600ms 才可见；这 600ms 内状态栏可能已经显示完成，
此刻用户全选复制拿到的是部分文本。

**R5 只补「增长」，不回放「倒退」。** `L_arrive` 变短，或消息被整条替换（重开会话、读库回填、切标签），
直接令两者相等。补间不服务倒退，倒退时演动画只会让人怀疑消息被改写。

**R6 不切开代理对。** 截断位置落在 UTF-16 代理对中间时回退 1 个码元 —— 半个 emoji 比晚 16ms 难看。

**R7 只动末尾，不动布局。** 不引入整块淡入 / 位移 / 缩放（不用 transform、opacity 做整条消息的过渡）；
「文本只增不减」这个既有前提不变，所以滚动跟随与锚点逻辑不需要改。

**R8 可关，关掉即改前。** 设置「外观 → 流式补间」默认开。关闭时渲染路径与改前**逐字节一致**：
`message.text` 直接进 `renderText`，不挂 rAF、不加包裹节点、不加 `data-*` 标记
（探针读 `textContent.length`，不依赖标记；为测试加标记会破坏这条等价）。

**R9 系统「减少动态效果」等同关闭**（`prefers-reduced-motion: reduce`）。这条是实现侧的兜底，可以否决。

### 14.2 验收读数（DOM 数值，不看图）

1. **追帧单调**：流式期间每 16ms 采 `[data-message-id="…"]` 的 `textContent.length`，序列单调不减；
   任意时刻末值 ≤ 该条回答的全文长度。
2. **收口有界**：正常结束后 ≤ 600ms 内显示长度等于全文；停止 / 出错为 ≤ 1 帧（≤ 34ms）。

- 光标重做：`.sc-caret` 保持原样。
- 用显示长度驱动任何持久状态或指标：见 R1。

## 15. agent 正文的 markdown：只买词法，自己渲染（2026-10-26 定）

正文现在是纯文本（`whitespace-pre-wrap`），代码块、表格、列表全挤成一坨段落 —— 这是「正文可读性」最大的缺口。
所有者 2026-10-26 拍板走 **A 方案：只引 `marked` 的词法层**（`marked.lexer(src)` → token 树），
token 自己映射成 React 元素。

**M1 只买词法。** 依赖只有 `marked`（^18.1.1，MIT，0 运行时依赖），且只用 `marked.lexer`；
不用它的 Renderer/Parser，不产出 HTML 字符串，**全程不碰 `dangerouslySetInnerHTML`**。
三条理由缺一不可：① 样式归我们（样式棘轮才管得住）；② agent 正文属不可信输入，不过 innerHTML 就没有 XSS 面；
③ 补间让显示文本每帧变，词法层必须便宜（实测 2288 字 0.31ms，占一帧 1.9%）。

**M2 块级白名单。** 只渲染：段落、标题、围栏代码块、列表（含嵌套与任务列表）、引用、表格、分隔线。
`html` / `tag` / `def` 这几类 token **一律降级成纯文本行**：正文里写 `<div>` 就该显示成 `<div>` 四个字符，
不许变成 DOM。不认识的新 token 类型同样降级（白名单之外一律走兜底，不猜）。

**M3 内联白名单。** 只渲染 text / strong / em / del / codespan / link / br；内联 `html`、`tag` 降级成文本。
`image` **不加载远端资源**：渲染成「`[图片] 说明文字`」的纯文本片段（点开与否则随链接策略，见 M4）。
理由：一张图会在你不知情时向外部发请求，而 agent 正文里出现图本来就是少数。

**M4 链接：只放行 `http` / `https` / `mailto`，且不许自带导航。** 其它 scheme（`javascript:`、`data:`、`file:`）
降级成纯文本，不给可点样式。放行的链接点击后**复制地址并短暂提示「已复制」**，
绝不让 WebView 自己导航（当前仓里没有任何外链打开通道，`<a href>` 直接点会把整个应用页换掉）。
「在系统浏览器里打开」需要 `tauri-plugin-opener` + capability 配置 —— 属新依赖，等所有者单独拍，
在那之前不给假入口。

**M5 代码块。** 等宽字体、横向滚动、不折行；右上角显示语言标签（有 `lang` 才显示，没有就不占位）；
内容原样（只去掉末尾空行）。**不做语法高亮**：那要 shiki 级依赖，跟 E5 长列表一起单独定。

**M6 表格。** 外面套横向滚动容器（表格不许撑破消息宽度），首行表头带底色，单元格对齐按 `align`；
列数不一致时按行补空、不丢内容。

**M7 流式中的不完整块照 marked 给的 token 渲染，不额外「等闭合」。** 真机实测（v18.1.1）：
未闭合围栏 → `code` token（照常当代码块，只是还会继续长）；半截表格 → `table`（已到的行照常成行）；
半截 `**粗体` / `[链接](` → 仍是一个 paragraph，星号方括号原样显示。
理由：补间把文本一帧帧拉长，任何「等闭合再渲染」都会在收口时让整块格式跳一次 —— 那正是 §14 刚去掉的观感。

**M8 解析在渲染层，按「显示文本」走。** `useMemo(normalize(marked.lexer(displayed)))`；
数据面（`message.text`、落库、轨迹面板）仍是原文，一个字都不改。

**M9 空内容不渲染空壳**：全空白或只有空行时不产生任何块。

**M10 流式光标归 Markdown 渲染。** 正文变成块级元素之后，父级 `.sc-caret::after`（inline-block）
会被挤到最后一个块**下面一行**，所以光标由 `<Markdown caret>` 渲染在最后一段行内文本的末尾
（新类 `.sc-caret-inline`，与 `.sc-caret` 共用 keyframes）。`.sc-caret::after` 保留给纯文本分支。

**M11 正文的空白语义交还给 markdown。** 这个分支不能再带 `whitespace-pre-wrap`
（那是纯文本时期的补丁）：markdown 段落里的软换行必须按空格折叠，否则 agent 按 80 列折行的正文
会变成满屏硬换行。`text.user` 分支保持 `whitespace-pre-wrap` 不变（用户输入是纯文本）。

**字号只借现有档，不新增**：h1/h2 → `text-body` + 中等字重，h3–h6 → `text-ui` + 中等字重；
标题**最多比正文大一档**，不许到 `text-lead` / `text-title`（消息头上的名字是 `text-caption`，
拿它当上限会把标题压到比正文还小，所以这里按正文而不是按消息头来定）。

                             链接 scheme 校验、list.start 归一、表格对齐归一
src/lib/markdown.test.ts     纯函数单测（不碰 DOM）

### 15.2 验收读数（DOM 数值，不看图）

1. **块级覆盖**：一段含 h2 / 有序列表 / 嵌套列表 / 表格 / 围栏代码 / 引用 / 分隔线的回答，
   DOM 里 `h2`、`ol>li`、嵌套 `ul` 层数、`table>tbody>tr`、`pre>code`、`blockquote`、`hr` 的数量与 token 数一致。
2. **危险输入不生效**：正文写 `<img src=x onerror=alert(1)>`、`<script>alert(1)</script>`、
   `[x](javascript:alert(1))` —— DOM 里不得出现 `img` / `script` 元素，链接不得带 `javascript:` href（降级为文本）。
3. **不完整输入不崩**：未闭合围栏 / 半截表格 / 半截粗体三种，界面照常渲染、控制台无报错。
4. **性能**：≥2000 字回答 + 补间开启，`PerformanceObserver("longtask")` 记录不得出现 > 50ms 的长任务；
   单次解析 ≤ 1ms（实测 2000 字：热态中位数 0.761ms、冷启动 1.344ms；单测回归线设 5ms 只防病态）。
5. **关闭补间（§14 R8）时 markdown 照常工作**，且 DOM 与开启时一致（补间只影响文本长度，不影响结构）。

### 15.3 外链打开方式（2026-10-26 拍板，走「自己加命令」）与后续安排

- **单击 = 复制地址**（保持，带「已复制」提示）；**`Ctrl/Cmd + 点击` 或中键 = 系统默认浏览器打开**。
  按钮 `title` 写清这两档：「单击复制 · Ctrl+点击在浏览器打开」。
- 打开通道是仓内自己的命令 `open_external(url)`，**不引 `tauri-plugin-opener`**：一个功能不值得引一套
  capability 权限模型，而且我们本来就有一条 IPC 通道与错误码体系。
- scheme 白名单 `http` / `https` / `mailto`，**前后端各校验一次**（前端降级成文本，后端拒绝）。
  后端拒绝返回 `50100`（入参不合法）；起浏览器失败返回 `50705`（辅助设施）。
  额外拒绝含控制字符（换行 / 制表）的 URL —— 那类串进命令行会被截断或注入。
- Windows 用 `cmd /C start "" "<url>"`：`start` 的第一个引号参数是**窗口标题**，必须先给一对空引号，
  再单独引住 URL，否则 URL 里的 `&` 会被 cmd 当命令分隔符。进程加 `CREATE_NO_WINDOW`，不闪黑框。
- **起进程是 fire-and-forget**：拿不到「浏览器真的开了」这一事实，所以前端不许假装成功
  （成功不弹提示；只有命令返回错误时显示「打不开」）。
- 待所有者拍：`mailto:` 目前放行（会拉起邮件客户端），若觉得吵可以收窄成只有 `http(s)`。
- **后续安排 · @handle 高亮**：markdown 接管正文渲染后，`text.agent` 分支不再对 `@短名` 着色
  （`renderText` 只保留在用户 / 系统 / 派活卡等纯文本分支）。要做的话落点是 markdown 的内联层：
  在处理 `text` token 时按已知短名拼 alternation 再切分成多个内联片段（长名优先，避免
  `@hermes-测试2` 被 `@hermes-测试` 抢先匹配），而不是回到整段字符串替换。**不在本批范围**，
  等正文里真的经常出现 @ 再排。

### 15.4 markdown 元素的样式必须落在设计语言里

规则只有一条：**markdown 元素和仓里别的控件用同一套令牌**，不许因为「它是第三方内容」就另起一套数值。
按 `docs/design-language.md` 对照后的具体口径：

- **行内代码**：圆角 `--radius-mark`（6）、底 `--s3`、边 1px `--l1`（改前是散值 5px）；
- **代码块**：圆角 `--radius-card`（12）、底 `--s0`（§1.1 指定的「代码块底」）、边 1px `--l1`、
  内边距走间距档（12 / 16，改前 14px 不在档位内）；语言标签 `text-micro` + `--i3`；
- **表格**：整张表一个圆角 `--radius-card` + 1px `--l1` 外框，圆角靠外层容器裁切
  （容器 `border + border-radius + overflow-x: auto`），单元格只画内部横竖线
  （`border-collapse: collapse` + 单元格 `border-right`/`border-bottom`），否则外框与会首/末行单元格
  会叠出双线与直角；表头底 `--s2`；
- **引用**：左侧竖线 **1px** `--l1`（设计语言规定边框只有 1px，改前 2px 违规）、文字 `--i2`；
- **分隔线**：1px `--l1`，上下间距走档位；
- **标题**：只用现有字号档（`text-body` / `text-ui`）+ 中等字重，字色继承 `--i1`；
- **链接**：色 `--a1` + 下划线（§1.4 指定 `a1` = 链接），hover 只在令牌内变化，不放大、不改色相；
- **禁止**：任何十六进制 / `rgb()` / `hsl()` 字面量与任意值（`border-radius: 10px`、
  `padding: 14px` 这种散值一律换成 `var(--radius-*)` 或档位内的值）。
- **例外**：**代码块整体**不受本节约束 —— 底色、边框、圆角、内边距、字族/字号/行高与 token 配色
  都归代码主题（§20），本节关于代码块的那一条已作废。行内代码**不**在豁免范围。

### 15.5 已知行为（查过了，不是我们代码的缺陷）

这两条都在 2026-10-26 定性过一次，先记录、不修。将来觉得碍事，按这里写的代价重新评估。

**K1 裸 URL 会把紧跟的标点吞进链接。** GFM 的 autolink 规则是「URL 一直延伸到空白或 `<` 为止」，
尾部只裁 `?!.,:*_~` 与多余的 `)`；`}`、`]`、引号**不在**裁剪集合里。所以 agent 把 JSON 直接贴进正文
（不包代码块）时，`"url":"http://127.0.0.1:7331/","headers":[]}]` 会渲染成一个 href 为
`http://127.0.0.1:7331/","headers":[]}]` 的链接，显示文本与 href 一致。
- 定性依据：同一段原文在 `marked` 与 `micromark + gfm`（GFM 参考实现）下都吞尾巴
  （micromark 只少吞最后一个 `]`），我们的映射层只是原样转发 `token.href`。
- 正确做法在源头：贴 JSON / 命令输出时包代码块。
- 如果哪天真要修：在映射层对 autolink 的 href 做尾部裁剪（多裁 `}` `]` `;` `"` `'`）。
  **代价是偏离 GFM**：真以这些字符结尾的 URL（带 `]` 的 wiki 链接一类）会被裁坏，
  而且显示文本与 href 会不一致。默认不做。
- 同源现象：`[文档](https://example.com/a）` 这种**全角括号不闭合**的写法，markdown 链接语法没闭合，
  会退化成「字面文本 + autolink」，全角 `）` 也被吃进 URL（两个实现一致）。

**K2 外链打开后浏览器窗口不一定是立刻到前台。** `open_external` 走 `cmd /C start "" "<url>"`，
前台权的传递链是 sincearc → `cmd.exe`（新进程）→ ShellExecute → 浏览器（常转交给已运行的实例）。
- 实测（PowerShell 每 120ms 采 `GetForegroundWindow`，采前先把 SinceArc 提到前台）：
  冷启动浏览器约 2.7 秒后转前台、热启动约 4 秒后转前台；两次前台最终都落到了浏览器。
- 排除的可能性：`tauri.conf.json` 没有 `alwaysOnTop`，采样里前台先在 SinceArc、
  随后转到浏览器 —— 所以不是我们的窗口压着。
- 剩下的原因是 Windows 前台锁（只有当前前台进程及其直接子进程有设置前台的机会）+
  浏览器自身「已有窗口时是否抢焦点」的策略。**不是浏览器故障，也没有我们这一侧的确定性修法。**
- 若将来要压缩延迟，按顺序试：① 去掉 `cmd.exe` 中间层，直接 `ShellExecuteW`（前台权直接归我们）；
  ② 启动前 `AllowSetForegroundWindow(ASFW_ANY)` 显式让渡；③ 枚举浏览器窗口 `SetForegroundWindow`
  （最脆弱，不建议）。①② 合计约 30 行 Win32，**不保证成功**：浏览器坚持不抢焦点时，
  客户端任何努力都盖不过它（只会任务栏闪）。

## 16. 统一 Tooltip：自研原语取代原生 `title`（2026-10-26 定）

原生 `title` 全部落到 WebView 自己的 tip 上，四个问题都不在我们手里：延迟由浏览器决定（0.5~1s，
和 `--dur-*` 不是一套）、样式不可控（深色下是系统浅色方块）、多行长文本会撑成大白板、
不响应键盘 focus。全仓 `title=` 现状 **26 处 / 16 文件**（2026-10-26 实测，`src/**/*.tsx`；
卡片上的 54 处是 2026-10-24 的旧读数，E12 重写后已减半）。

### 16.1 契约

`src/components/ui/Tooltip.tsx`，自建原语，不引第三方库。

| 项 | 规定 | 为什么 |
| --- | --- | --- |
| 打开 | hover **220ms**；`focus-visible` **立即**开（不等延迟） | 与 §3.4a HoverCard 同一组数字；键盘用户已经表达了意图，再等就是慢 |
| 关闭 | 指针离开 **140ms**；Esc 立即；滚动 / 切视图立即 | 手抖掠过不该有反应；滚动时浮层留在原地会显得错位 |
| 触屏 | `pointerType === "touch"` 不开 | 触屏没有 hover，弹出来就是挡内容 |
| 定位 | 默认在锚点**上方**（间距 6px），放不下翻下方，水平夹进视口 | 与 HoverCard 相反：tip 是短提示，优先不挡被说明的控件下方内容 |
| 挂载 | `position: fixed` + `createPortal(document.body)` | 面板里有 `backdrop-filter` 与 `overflow-hidden`，不 portal 会被裁/糊 |
| 外观 | **平铺**：`--s2` 实心面 + 1px `--l1` 边框（**不用** `.sc-glass`、无内边缘高光、无外投影）+ `radius-mark`(6) + `text-caption`；内边距 6/8；最大宽 **280px**，可换行 | 圆角比卡片小一档：tip 不是卡片；提示要「被看见」，所以在暗色下破例给边框（§1.8 已记） |
| 无障碍 | `role="tooltip"`、`aria-describedby` 指向浮层 id | 读屏能读到；同时**不许**再挂 `title` 兜底（两套提示同时出现是最难看的状态） |

### 16.2 内容边界（决定用哪个原语）

- **≤ 24 字、单行短提示** → Tooltip。
- **> 24 字、或需要结构化（多行/键值/可复制）** → HoverCard（§3.4a），不要用 Tooltip 兜大段文字。
- 已经可见的文字不要再做 tooltip（重复朗读，也多余）。
- **常识性交互不加提示**：拖拽把手（分栏、窗口边）、开关、滚动条、光标已经说明用途的图标按钮。
  判据：控件的外观 / `cursor` 已经表达了「能干什么」时，提示只是噪音（2026-10-26 所有者指出：
  「这种常识性的 UX 加上 tip 反而浪费视觉」）。分栏把手即按此条撤掉。

### 16.3 禁用元素

禁用元素**不挂 Tooltip**：禁用的 `button` 不触发 pointer 事件，tip 永远弹不出来（现在的
`Button` 用 `title={disabledReason}` 就是这种「看起来有、其实多数时候没有」的状态）。
禁用原因写在**同一行的可见文案**里，或做成点击后的 `role="alert"` 提示。

### 16.4 迁移与验收

分批：① 原语 + 高频三处（`StatusBar` / `TabStrip` / `Composer`）；② 设置页与成员表单
（`SettingsView` 4 / `AgentUsers` 2 / `McpCatalogSection` 2 / `Field` 1）；③ 轨迹面板与其余。

验收（真机读数，不是看代码）：

1. `grep -rc 'title="' src --include=*.tsx` 汇总为 **0**（`src/lib/**` 里的字符串不算）；
2. 打开延迟实测 **220ms ± 40ms**（CDP 注入 pointer 事件 + 采样浮层出现时刻）；
3. `focus-visible` 打开不延迟；Esc 与滚动均能收起；
4. 在带 `backdrop-filter` 的面板内（轨迹面板/设置页）不被裁，层级高于面板；
5. 触屏模拟（CDP `Input.dispatchTouchEvent`）不弹；
6. 禁用按钮 hover 不出 tip（本来就是「弹不出来」，换组件后仍然如此，但不再有隐形 `title`）。

## 17. Hint：显式说明入口（2026-10-26 定）

界面上有些解释是**常驻长文本**（设置项说明、能力矩阵注脚、存储提示脚注…）：占版面，又只有少数人读。
Hint 把它们收进一个「i」入口，让版面只留结论。组件名与概念名统一叫 **Hint**
（不叫 InfoDot / MoreInfoButton）。

### 17.1 与 Tooltip 的边界：按触发意图分，不按字数统一

| | Tooltip（§16） | Hint（本节） |
| --- | --- | --- |
| 触发 | 挂在既有控件上，用户**顺手一瞥** | 显式设立的说明入口，用户**主动索取** |
| 内容上限 | ≤ 24 字，单行 | **≤ 160 字 / 4 行**（超了走 HoverCard 或留在版面） |
| 为什么不同 | 没主动要的东西不该挡住视线 | 主动问的东西可以长一点，但再长就该换形态 |

### 17.2 形态与交互

- **触发体**：`i` 图标按钮（`--fs-caption` 大小的圆点/圆圈，`text-ink-3`，hover/active `text-ink-2`），
  `aria-label` 用「<被说明对象> 说明」；不占版面宽度（inline，跟在标题或标签后）。
- **悬停**：复用 Tooltip 浮层与延迟（220ms 开 / 140ms 关 / `focus-visible` 立即），
  所以 Hint 的浮层就是一个 Tooltip（同一套 `.sc-tooltip` 样式）。
- **点击或 Enter/Space：固定展开（pin）**，再点收起。这是触屏与键盘用户的唯一可靠路径——
  hover-only 在触屏上等于没有。
- **Esc 收起**；点击浮层外收起；固定态下不因 `pointerleave` 关闭。
- **无障碍**：触发体 `aria-expanded` + `aria-controls` 指向浮层 id；浮层 `role="tooltip"`，
  固定态给 `aria-live="polite"`（读屏能读到展开的说明）。

### 17.3 迁移判据：哪些常驻提示可以迁进来

**可以迁**：解释「这是什么 / 为什么这样 / 取值范围」的补充说明、术语与单位、实现细节注脚。

**不许迁**（必须留在版面上）：

1. 操作前必须读的后果提示——破坏性、不可逆、涉及权限/计费（例：「此项会断开当前会话」）；
2. 状态与错误文案（错误原因、当前连接态、校验失败）；
3. 必填标记与格式要求；
4. 用户不点这个 Hint 就没法完成任务所需的信息（主谓信息不能藏）。

判据一句话：**「漏读这条会不会导致误操作？」会 → 留在版面；不会 → 可迁。**

### 17.4 验收

1. 触屏点击可展开（CDP 触摸事件），键盘 Enter/Space 可展开，Esc 与点外可收起；
2. 固定态在 `pointerleave` 后不消失，直到用户收起；
3. 说明文字进无障碍树（`aria-controls` 指向的节点可读）；
4. 迁移前后**同一视图的可见文字行数**对比（真机读数，逐视图记录）；
5. 迁移清单逐条标注「可迁 / 不许迁 + 理由」，经所有者过目后才动手。

## 18. 代码高亮：只买词法，配色归我们（2026-10-26 定）

### 18.1 选型（实测，不是印象）

60 行 TypeScript、同一台机器、浏览器/Node 双份读数：

| 方案 | 体积 min/gzip | 60 行耗时 | 输出 | 结论 |
| --- | --- | --- | --- | --- |
| **prismjs 1.30.0**（core + 语言） | 27 KB / **10 KB**（3 语言） | 热 **0.27–1.4 ms**，冷 9–13 ms | token 树 | **采用** |
| lowlight + 5 语言（hl.js 引擎） | 43 KB / 16 KB | 5.6 ms | hast | 备选：引擎最主流，代价 +6 KB 与 4× 解析 |
| shiki core + JS 引擎 | 392 KB / 77 KB | 125.9 ms | token 树 | 否：慢到不可用 |
| shiki core + oniguruma | 949 KB / 286 KB + wasm 455 KB | 44.5 ms | token 树 | 否：体积与耗时都不值 |

决定性理由不是「Prism 最流行」（它不是，周下载 21.3M 低于 highlight.js 的 24.1M），而是两条：
① 它原生给 **token 树**，我们全程不碰 `dangerouslySetInnerHTML`；② 体积与耗时最省
（shiki 的 JS 引擎 126 ms、oniguruma 44 ms + 455 KB wasm，都不可接受）。

> 2026-10-26 修正：当时还写了「设计语言是暗色单色、配色必须自己写」—— **该理由已作废**。
> 代码块配色现在走成熟代码主题并**豁免**单色设计语言，见 §20。

### 18.2 抽象层（换库只改一个文件）

```
src/lib/highlight/types.ts    TokenSpan { text, theme } + HighlightTheme（9 档）+ Highlighter 契约
src/lib/highlight/prism.ts    适配器：Prism token 树 → 语义档位；语言别名表也在这
```

- 调用方**不许**直接 `import prismjs`；只认 `Highlighter.tokenize(code, lang) → TokenSpan[]`。
- `HighlightTheme` 只有九档：`plain / comment / keyword / string / number / literal / function / type / operator / punct`。
  新增档位要改契约，不许在适配器里私造。
- 配色表在我们这层：`src/lib/highlight/themes.ts` 提供多套代码主题（见 §20），
  **不套用库自带的主题对象**，也**不受单色设计语言约束**。

### 18.3 语言集与降级

- 内置：`ts/tsx/js/jsx/json/bash/sh/sql/python/rust/css/html/markdown`（附别名 `py→python`、`postgres/sqlite→sql` 等）。
- **未标注语言**、或标注了我们不支持的语言 → **纯文本渲染**，不猜、不报错、不显示「不支持」的噪音。
- 单块 **> 500 行**不自动高亮（渲染纯文本 + 一行 `高亮已省略（N 行）`）：长日志不值得为配色卡住滚动。
- 同一 `(lang, code)` 的 token 结果做 LRU 缓存（上限 200 条），滚动回来不重算。

### 18.4 验收（真机读数）

1. `dangerouslySetInnerHTML` 全仓 **0 处**（守卫测试）；
2. 60 行 TS 块 token 数约 4600、热态 ≤ 1.5 ms（冷态 ≤ 15 ms）；
3. 未标注语言的块与未知语言的块都渲染为纯文本，且**无** token span；
4. 501 行的块降级为「高亮已省略」；
5. 同一块滚动出视口再回来，不重复解析（缓存命中计数）。

## 19. 长列表：窗口化 + 三条我们自己必须保住的语义（2026-10-26 定）

### 19.1 选型与目标

- 库：**@tanstack/react-virtual 3.14.23**（33 KB / **10 KB gzip**，MIT，peer 支持 React 19，今日仍在发版）。
  手写被否：库覆盖了最难的两项（动态测量、窗口计算），手写要重写这些且更容易错。
- 量级目标：单会话 **2000 条消息** / **5 万条轨迹**；DOM 常驻行数 ≤ 30；滚动帧 p95 ≤ 20 ms、**0 帧 > 33 ms**；
  首屏可见 ≤ 150 ms。

### 19.2 抽象层（换库只改一个文件）

```
src/lib/virtual/useVirtualList.ts
  api: { rows, totalSize, measureRow, scrollToIndex, scrollToEnd, atBottom }
```

调用方不许 import `@tanstack/*`。

### 19.3 三条语义必须写在抽象层里（spike 实测支撑）

| 语义 | 库是否提供 | 实测 |
| --- | --- | --- |
| 贴底跟随（新消息 + **总高变化**） | 否（只认识条数） | 我们自己写后：最后一条 +160px，间隙 0 → 0 |
| 上翻后不被拉回底部 | 否 | atBottom=false 时增长不劫持（实测成立） |
| 上方条目变高时保持锚点 | **实测未生效**（scrollTop 未变，位移 200px；显式谓词 `() => true` 也无效） | 必须自己写锚点恢复：记 `{anchorIndex, offsetInViewport}`，变化后摆回 |

锚点恢复的落点：`useVirtualList` 内部（约 30 行）。换库时这三条语义跟着抽象层走，不会丢。

### 19.4 硬约束

- **消息行高度必须由内容决定**（`min-height` 起步），**禁止**把 `height` 写成 `row.size` ——
  那样会掐死 `measureElement` 的测量通道（spike 第一版就是这么错的，量出来的 200px 位移是假象）。
- 估算高度按消息类型给初值：纯文本 72 / 带代码块 200 / 带表格 260 / 轨迹行 56；实测后覆盖。
- 历史分页加载（向上补历史）必须保持当前位置：加载前后用锚点恢复，不许让用户「被拽走」。

### 19.5 验收（真机读数，造数后量）

1. 造数：单会话 2000 条消息；轨迹按 §19.6 的口径造「200 轮 × 200 事件 ≈ 4 万活动」（整批可删；量完删除并核对计数回到造数前）；
2. 首屏可见时间、滚动帧 p50/p95/max、DOM 行数、内存（`performance.memory` 或任务管理器）；
3. 贴底跟随、上翻不劫持、上方变高锚点恢复、历史加载保位 四项各一条读数；
4. 轨迹面板同样走同一套 hook（第二个调用方），不许复制一份窗口逻辑。

## 20. 代码配色主题：markdown 代码块豁免单色设计语言（2026-10-26 所有者拍板）

### 20.1 为什么豁免

代码块是**阅读界面**，不是产品的视觉资产：配色只要影响「能否一眼分出关键字 / 字符串 / 注释 / 数字」。
市面上的成熟主题经过大量真实代码验证，我们自造的灰阶映射反而把可读性做没了（实测字符串与正文
同色 `#f6f6f6`，九档里只有注释和数字能看出差别）。所以：

- **整个 markdown 代码块豁免设计语言**：容器背景、边框与圆角、内边距、字族 / 字号 / 行高，
  以及九档 token 配色，全部由代码块自己的样式与代码主题决定，**不再引用 `--radius-*` / `--s*` /
  `--fs-*` 这些令牌**（`docs/design-language.md` §1.12 记例外）；
- 例外的**边界是「代码」本身**：围栏代码块 + 行内 code 之外的任何元素（正文、表格、引用、链接、
  按钮…）仍只用设计语言令牌；
- **行内 `code` 也走代码主题**（2026-10-26 所有者口径）：前景用主题的 `plain` 色，底色用主题的
  代码底色，边线由主题前景色派生（不做 token 化 —— 行内片段脱离上下文猜语言只会错）。
  一句话口径：**凡「是代码」的地方都用代码主题配色；不是代码的地方一律走设计语言**；
- 几何（圆角 / 内边距 / 字号 / 行高）在四套主题之间**保持一致**：主题只负责配色，避免同一产品里
  换个配色块形状就跳变。几何值集中写在 `src/styles.css` 的代码块变量里（`--code-radius` /
  `--code-pad-x` / `--code-pad-y` / `--code-font-size` / `--code-line-height`），不挂设计语言令牌。

### 20.2 契约

```ts
// src/lib/highlight/themes.ts
type CodeThemeId = "github-dark" | "one-dark" | "dracula" | "nord";
type CodeTheme = {
  id: CodeThemeId;
  label: string;            // 设置页显示名
  background: string;       // 代码块底色，只允许 #rrggbb
  colors: Record<TokenKind, string>;  // 九档全部要给，缺一档即视为非法
};
```

- 九档与 §18.2 的 `HighlightTheme` 完全一致，**不新增档位**；
- 色值只允许 `#rrggbb`（不许 `rgb()` / `hsl()` / 令牌引用）——主题表要能被单测逐条校验；
- 五套：**sincearc（默认）**，以及 **github-dark / one-dark / dracula / nord**（公开配色，不自创，原样取用）；
- **sincearc 是为本站设计的一套**（2026-10-27 所有者定：SinceArc 作默认）—— 不是把界面令牌硬套到代码上，
  而是以品牌面阶 `--s0` `#292d3e` 为底、冷白文字为基准，语义色按色相分开，
  **每档与底色对比度 ≥ 5:1**（注释 5.02 最低；普通文本 AA 门槛 4.5）：

  | 档位 | 色值 | 对比度 | 用途说明 |
  | --- | --- | --- | --- |
  | plain | `#e6e9f2` | 11.24 | 标识符与标点以外的一切 |
  | comment | `#949cba` | 5.02 | 刻意压低，读代码时能跳过 |
  | keyword | `#9db4ff` | 6.76 | 关键字（冷蓝，与品牌同色相） |
  | string | `#8fd4a8` | 7.89 | 字符串 |
  | number | `#f0c674` | 8.47 | 数字（暖金，与品牌 `--warn` 同族） |
  | literal | `#f0a48c` | 6.75 | `null` / `true` / `false` 这类字面量 |
  | function | `#7fd0e6` | 7.84 | 函数名 |
  | type | `#c9a0f0` | 6.35 | 类型、类名 |
  | operator | `#c3cae0` | 8.35 | 运算符（结构记号，压低饱和度） |
  | punct | `#aab2c8` | 6.44 | 标点（结构记号，压低饱和度） |
  | 底色 | `#292d3e` | — | 品牌面阶 `--s0` |

- 默认值只有一个来源：Rust `DEFAULT_CODE_THEME` 与 TS `DEFAULT_CODE_THEME_ID` 都必须是 `sincearc`，
  两边一致有测试守；读库遇到未知 id 一律回落它。
- 主题**只改颜色，不改 token 化流程**：仍是 Prism 出 token 树、我们逐 span 渲染，全程不碰
  `dangerouslySetInnerHTML`。

### 20.3 落地点

- 根节点属性 `data-code-theme="<id>"`；`src/styles.css` 在 `[data-code-theme="…"]` 下定义
  `--code-plain/--code-comment/--code-keyword/--code-string/--code-number/--code-literal/
  --code-function/--code-type/--code-operator/--code-punct/--code-bg`；
  `.sc-prose [data-token="…"]` 只引用变量，**组件里不出现色值**。
- 设置项 `code_theme`（字符串 id）走既有 settings kv；未知 id 或读不到 → 回落 `github-dark`（默认）。
- 行内 `code`：`color: var(--code-plain)`、`background: var(--code-bg)`、`border: 1px solid
  var(--code-inline-border)`（`--code-inline-border` 由主题前景色派生，如
  `color-mix(in srgb, var(--code-plain) 18%, transparent)`），圆角取 `--code-radius`；不再用 `--s3`/`--l1`。
- 设置页「外观」分区用**缩略图选择器**（不是分段控件）：每套主题一张卡，卡内用该主题的**真实配色**
  渲染同一段样例代码（容器带 `data-code-theme="<id>"` 与 `data-code-tokens`，样例 tokens 走 `data-token`），
  卡下是主题名；选中态 = 1px 强描边 + `aria-checked="true"`；

### 20.4 边界

### 19.6 轨迹面板：列表虚拟化 + 图视图阈值（2026-10-27 定，替代 §19.5 里「5 万条轨迹」那条）

**先讲清楚一个现状**（读代码确认，不是推测）：`session_trace` 在服务端把 `limit` 夹到 **200 轮**、
事件按 `limit × 200` 取；前端目前只请求 **50 轮**。所以面板单次能看到的量级是「50 轮 ≈ 最多 1 万条活动」
到「200 轮 ≈ 最多 4 万条活动」——**五万条轨迹今天根本进不了界面**。
§19.5 原来把「5 万条轨迹」写进本批验收，是实现够不到的口径，本批改成下一条的读数，
「翻得到五万条」另立卡（E18.1 轨迹分页：后端游标 + 前端拼接 + 前插锚点）。

**取数量与成本（实测）**：服务端上限 200 轮，前端一次只拉 **50 轮**（≈1 万条活动，IPC 314 ms）；
200 轮 ≈ 4 万条活动的成本是 IPC **1213 ms** / 9.1 MB、冷开面板 **1574 ms** —— 这个体感不该做默认，
「翻更早」交给轨迹分页（E18.1 / t_18136eb8，规范写 §19.7）。下面 4 万那组读数是临时把上限抬到 200 轮量出来的。

- **列表视图**接入 `useVirtualList`（第二个调用方，不许复制一份窗口逻辑）：
  把「轮标题 + 该轮活动行」拍平成一维 items（`t:<turnId>` / `a:<activityId>`），行高由内容决定；
  DOM 常驻 ≤ 30 行；定位/聚焦改走 `scrollToIndex`，不再靠 `scrollIntoView` 逐个 ref。

  顶部一行说明「轨迹过多（N 条活动），图视图已省略」；阈值以下照旧可切。
- **边界**：容器 resize 不丢位置（允许 ≤ 1 行高的漂移）；空会话沿用既有空态；切视图时按轮 id → index
  尽量保持当前位置。

**「有轮、零活动」不是空会话，也不是应该画图的东西（2026-10-27 补）**

**复盘：这批为什么会先在造数会话里被发现**（2026-10-27）

## 20. release 构建禁用右键菜单（2026-10-27 拍板）

**拍板**：release 构建屏蔽，dev 构建保留（排查时要用「检查」）。

## 21. 进行中的一轮：活动行自述（2026-10-28 定）

**决定**：删掉输入区上方那条全局写提示（`app.writeHint.*`），把「谁在写什么」并进消息流里
**每个 agent 自己的活动行**。输入区上方不再留任何调用状态条。

**为什么**：那条提示是「消息流之外只能用一条代表多个 agent」的妥协 —— `summarizeLocks` 取 `locks`
的第一条作代表、`extra = 条目数 - 1` 凑出「另有 N 个进行中」。而每个 agent 本来就有**且只有一条**
running 活动行（`activity.id === "act-stream-<acpSessionId>"`，起轮时先 filter 同 id 再 push），
所以「每人一行、各自自述」是现成的结构，不需要那条全局摘要。

### 21.1 每行四段

| 段 | 内容 | 规则 |
| --- | --- | --- |
| 左 | 状态标签 | **切换，不是并列**：ACP `tool_call.kind` 缺省或 `think` → 「思考中」；其余（`read` / `edit` / `execute` / `search` / …）→ 「调用工具中」。同一时刻只有一个标签在 DOM 里 |
| 中·主行 | `title` | 取 ACP `tool_call.title`（如 `Edit src/App.tsx`）；thinking 时是「思考中」那类标题 |
| 中·次行 | `activity.body` 的首行 | 即 `rawInput` 展开后的首行，等宽、单行截断（`truncate`）。`body` 缺失、空串、或全空行 → **整行不渲染**（不留空白行） |
| 右 | `FileLock` 图标 + `×N` | 只在该 agent **有写锁**时出现；`count > 1` 才跟 `×N`；Tooltip 显示锁的文件（长路径显示尾段） |

**`detail` 不再承载 rawInput**：`tool_call` 处理时写 `title` 与 `body`（`body = rawInputLines(rawInput).join("\n")`），
不写 `detail` —— 否则主行与次行会把同一条命令显示两遍。`detail` 只留给思考类活动使用（有才显示，没有不占位）。

`rawInput` 展开复用 `src/lib/trace-adapter.ts` 的 `rawInputLines()`，不要在前端另写一套；
后端已把 `rawInput` 单字段截断到 16 KB（`docs/acp-notes.md`「轨迹 payload」），这里只按显示宽度截断，不做二次丢弃。

### 21.2 写锁归属

- 从 `activity.id` 取 `acpSessionId`（`act-stream-` 之后的部分），查 `session.locks[acpSid]`。
- **只显示该 agent 自己的锁**，不再有跨成员的「另有 N 个」。
- 当前活动是 `read`、但该 agent 手上压着一条 `edit` 的写锁 → **照常显示锁图标**。这是融合的主要收益：
  以前提示条与活动行各说各的，这种组合态看不见。
- `locks` 里没有该 `acpSid` → 不渲染图标、不占位。

### 21.3 数据来源

活动行的 `title` / `detail` / `rawInput` 来自 ACP 的 `session/update`：`tool_call` 与
`tool_call_update`（后者是增量，合并语义见 `docs/acp-notes.md`：`null` 不覆盖）。
payload 形状：`{ toolCallId, title, kind, status, rawInput?, content?, locations? }`。
`kind` 是 ACP 的枚举（`read` / `edit` / `delete` / `move` / `search` / `execute` / `think` / `fetch` / `other`），
映射到前端 `ActivityKind` 时**只用于决定「思考中 / 调用工具中」这一处判断**，不改变轨迹面板的分类口径。

**`status` 的处理**：`pending` / `in_progress` 更新活动行；`completed` / `failed` **不重置**活动行 ——
它继续显示最后一次调用的 `title` 与 `rawInput`，直到下一次 `tool_call` 覆盖或这一轮终态。
理由是短工具连续调用时重置会让标签在「思考中 ↔ 调用工具中」之间来回跳；
而「刚跑完什么」比「现在大概在思考」信息量更大。轮终态由既有路径收口，这里不碰。

### 21.4 配色

- 锁图标 `text-ink-3`，**不用** `warn-1` —— 写锁是状态，不是告警。
- 标签、次行沿用现有 `text-caption` / `font-mono text-micro`，不新造颜色、不新增令牌。

### 21.5 不动的部分

- 已结束的历史活动行（`status !== "running"`）与 `TracePanel` 的渲染路径。
- 输入区其它元素（用量行、停止提示、`isStopping` 条）。

### 21.6 验收（DOM 数值，不看图）

1. 一行里状态标签数量 = 1；`thinking` 时为「思考中」，工具调用时为「调用工具中」。
2. 带 `rawInput` 的工具行有次行且 CSS 为 `text-overflow: ellipsis`；无 `rawInput` 的行次行不存在（不是空 div）。
3. 有锁时 `FileLock` 图标出现；`count = 1` 时无 `×N`，`count = 2` 时有。
4. 悬停图标出现 Tooltip 且含文件名。
5. 输入区上方不再有 `app.writeHint.current` / `app.writeHint.extra` 渲染出的元素。
6. 两个 agent 同时 running（群聊）→ 两条行各自显示自己的标签与锁，互不串。

### 21.7 不做

- 不做全局「另有 N 个进行中」计数（跨成员并发由「多行同时亮着」自己表达）。
- 不把多个 agent 的活动合并成一条。
- 不给锁图标加文字标签（图标 + Tooltip 足够，避免整行三段文字）。

### 21.8 进行中行的 loading：S 作容器（2026-10-29 定）

**决定**：进行中行**左侧恢复一个动效指示**，但不用原来的三点，改用品牌 S 作容器；抽成独立组件
`ui/BrandLoader`，`variant` 三档（`comet` 默认 / `fill` / `draw`），三档都保留在代码里。

**为什么**：§21 把三点留在了历史行、进行中行换成标签，结果是**最该「在动」的那一行反而没有动的信号**——
标签是状态文字，不是活动指示。三点本身的问题不在「动」，而在它只表达「在动」、不表达归属与品牌；
S 是 `BrandMark` 的同一份几何，延伸即识别，且能长期循环而不用换姿势。

**动作（三档共用一套时序，只换「进度长什么样」）**：

| 阶段 | 时长 | 说明 |
| --- | --- | --- |
| 去程 | 1400ms | 起点 → 终点，两端 `ease-in-out`（往复才像呼吸，不是匀速传送带） |
| 到端停顿 | 60ms | 只为了让「到头」被看见 |
| 翻转 | 520ms | `scaleY(-1)`（上下反转），`ease-in-out`。**不低于 400ms**——200ms 那版看着像抽搐 |
| 回程 | 1400ms | **沿原路返回，不重置到起点**（回程里 S 是翻转态，亮点原地折返） |
| 再翻转 | 520ms | 回到正向，进入下一圈 |

一圈约 3.8s，无限循环。**「满格」不是语义**：这是 loading，不是进度条 ——
不显示百分比、不回调完成、不因为"走满"改变任何状态。

**三档 variant**（`variant?: "comet" | "fill" | "draw"`，默认 `comet`）：

| variant | 进度形态 | 实现 | 适用 |
| --- | --- | --- | --- |
| `comet` | 亮点 + 三层拖尾沿 S 巡游，折返时拖尾自动换到运动方向的反侧 | `path.getPointAtLength()` + rAF，拖尾偏移 70 / 140 / 210（1024 坐标系，**正的**，位置按 `d - dir*offset` 算） | 行内（默认） |
| `fill` | S 作遮罩，内部一条实心竖条被裁出 S 形往右扫，到端原地退回 | SVG `mask` + 竖条 `translateX(150→962)` | 需要"能读出到端"的场合 |
| `draw` | S 从起点圆点一笔写出来，到端沿原路把笔画收回去 | `stroke-dashoffset`（`L → 0 → L`） | 需要"书写感"的场合 |

**几何只有一份**：`S_PATH`、`S_GROUP`（`translate(46 46) translate(-197.6 -215.6) scale(1.386)`）、
`SWEEP_FROM/TO` 抽到 `src/lib/brand-mark.ts`，`BrandMark` 与 `BrandLoader` 共用，禁止在两处各写一遍 d。
`fill` 的遮罩里必须**同时**含路径与起点圆点，否则圆点永远暗着。

**尺寸与颜色**：`size` 14 / 16 / 20（行内默认 16）；一律 `currentColor`，由容器决定 ——
活动行里跟随 `player.color`（与原来三点一致），输入区连接态用 `text-ink-3`。
**16px 下行内 S 的描边约 1.6px**，`comet` 的亮点直径约 2.2px：这是选它的已知代价，
嫌细就在 `size` 上加到 20，不要改路径或加粗描边（那会让它偏离 `BrandMark`）。

**`prefers-reduced-motion`**：降级为静态 S + 透明度呼吸（0.45 ↔ 1，2.4s），**不做位移**，
不做翻转 —— 位移类动效对前庭敏感人群是硬伤，而 loading 的语义（"还在跑"）用呼吸足够。

**验收（DOM 数值，不看图）**：

1. 进行中行里 `[data-brand-loader]` 存在且 `width === height === size`；历史行仍是三点、没有该元素。
2. `comet`：单向内 head 位移单调，相邻采样步进 < 1.5 × 平均速（证明没有「重置回起点」的瞬跳）；
   折返只发生在翻转窗口内。
3. 翻转：`scaleY` 在 520ms 内**经过中间值**（不是 1→-1 瞬跳），且两次翻转之间差约 1.4s + 0.06s。
4. `fill` / `draw` 在探针页各渲染一份，尺寸与颜色与 `comet` 一致（只换形态）。
5. `reduced-motion` 下：无 `transform` 动画、S 静态可读。
6. 三档都只动 `transform` / `stroke-dashoffset` / 属性写值，**不改布局**（容器 rect 前后一致）。

**交接**：本决定即看板 `t_c322870d`（E15.3 BrandLoader）的落地口径，把那卡的「方案 A 单档」
扩展为「三档 + 往复动作」；`S_PATH` 抽常量、`reduced-motion` 降级、`ui/BrandLoader` 命名沿用该卡。

## 22. 输入区两行化：工具栏在上、输入框在下（2026-10-29 定）

**决定**：把 `Composer` 从「输入框 + 底栏」的上下顺序反过来 —— **上排工具、下排输入**，
整体拉高，外层玻璃底（`sc-glass` 的 `--edge-highlight` 内边高光）**保留不动**；
发送键从工具行里拿出来，**浮动在输入框右下角**。

### 22.1 结构

```
┌ sc-glass rounded-card ──────────────────────────── 外层（玻璃底 + 内边高光，保留）┐
│ ⌘ 附件   ACP · stdio            [MCP] [撤销 chip] [自动批准 ▾]   ← 工具行（上）    │
│ ┌ 1px border-line-1 ─────────────────────────────┐                               │
│ │ textarea（多行，可换行）                                    [■] [↑]            │ ← 发送浮动右下
│ └────────────────────────────────────────────────┘                               │
└───────────────────────────────────────────────────────────────────────────────────┘
```

| 元素 | 规格 |
| --- | --- |
| 外层 | 沿用 `sc-glass rounded-card`（`--glass-1` + `--glass-border` + `--edge-highlight`）；**不改**这三样 |
| 工具行 | 高约 28px，`px-2 pt-1.5 pb-1`；左：附件 → 状态标识（`ACP · stdio` / agent 输出）；右（`ml-auto`）：MCP → 撤销 chip → 自动批准档位 |
| 输入框 | `border border-line-1 rounded-control`，底色通透（不另铺实心，让玻璃底透出来）；`min-h-[76px]`、`max-h-50`（200px）保留 |
| 发送 | `absolute bottom-2 right-2`，不占布局；`size-7` 圆形，`variant="glass"` |
| busy 态 | 停止键（`Square`）在插话键**左侧**，两者同组浮动在右下 |

### 22.2 为什么不给输入框铺实心底

外层玻璃是「内边高光划界」的那一层（§1.8）。输入框再铺一层实心面 = 双层底，
高光就被埋在第二层下面，看起来像嵌了一个洞。所以输入框只加 **1px 暗淡描边**（`--l1`）
把编辑区域划出来，底仍透出玻璃。这也正是「保留内边高光的底色」的字面意思。

### 22.3 浮动键的避让

`textarea` 右侧留 `pr-[76px]`（busy 时含插话文字，留 `pr-[104px]`），保证长行文字不钻到按钮底下；
按钮组本身 `pointer-events` 照常，`textarea` 不被覆盖 —— 用 `absolute` 而不是负 margin。

### 22.4 不动的部分

- `mention`（@ 补全）、`slash`（/ 命令）、IME 组合期不发送、`Enter`/`Shift+Enter`、`submit()` 全部逻辑零改动。
- `SlashMenu`、`@` 候选浮层的位置（`bottom-full` 相对外层）—— 外层仍是同一个定位祖先。
- 撤销 chip、自动批准菜单、MCP 按钮的行为与顺序。
- 不做拖拽上传、不做附件真实读取（附件按钮仍是占位，与现状一致）。

### 22.5 验收（DOM 数值，不看图）

1. 工具行 `getBoundingClientRect().top` **小于** `textarea` 的 top（工具在上）。
2. `textarea` 计算样式 `border-top-width === "1px"`，颜色等于 `--l1` 的计算值；`min-height ≥ 76px`。
3. 发送按钮计算样式 `position === "absolute"`，其右边缘与输入框右边缘间距 ≤ 8px，底边同理。
4. 外层 `box-shadow` 含 `inset`（内边高光没被吃掉），`backdrop-filter` 含 `blur`。
5. 输入 60 个字符不换行时，文字右端与发送按钮左端不重叠（比较 `scrollWidth` 与可用宽度）。
6. `busy = true` 时停止键与插话键同时在右下，且停止键 x 更小。

## 23. 输入区按「窗口卡片」语言收敛（2026-10-29 定）

参考源：reactbits.dev 首页 `.lh-window` —— 从它构建产物 `index-*.css` 里读到的实测值，不是印象：

```css
.lh-window{
  border-radius:18px;
  background:rgba(24,21,30,.8);
  box-shadow: 0 30px 70px rgba(0,0,0,.36), 0 14px 32px rgba(0,0,0,.26),   /* 外投影 */
              inset 0 0 0 1px rgba(255,255,255,.08),                       /* 内描边 */
              inset 0 1px 0 rgba(255,255,255,.07);                          /* 顶部高光 */
  backdrop-filter:blur(24px) saturate(1.5);
  padding:0 6px 6px;          /* 标题栏贴顶，内容三边内缩 6px */
}
.lh-window-bar{height:36px}   /* 标题栏 */
.lh-window-status{height:32px}/* 底栏 */
```

**取**：半径 18px、`blur(24px) saturate(1.5)`、工具行 32px 的高度节奏。
**改**：参考的三边内缩 6px 收到 **4px** —— 18px 圆角 + 32px 工具行之下，6px 的下边与左右看起来都比
视觉重量更宽（所有者 2026-10-29 判定）；三边仍保持同一个值，不分别调。
**不取**：外投影（输入框在消息流里、不是浮层，压 70px 投影会让整条消息区发脏）；
**不取**暗色下的 `inset 0 0 0 1px`（与 §1.8「暗色靠内边高光划界」冲突 —— 浅色侧 `--glass-border` 本来就是 1px，两个主题各自守住自己的分界方式）；
**暂不取**半透明底色 `.8`：那要等窗口 `transparent` + Mica 定了一起做（§22 结尾），单独改 `--glass-1` 只会把不透明底搅浑。

### 23.1 四条改动

1. **外层**：`sc-glass rounded-card`（12px / blur 16 / saturate 1.6）→ `sc-window rounded-window`（18px / blur 24 / saturate 1.5）。新增 `--radius-window: 18px` 与 `.sc-window`，不动 `sc-glass`（全站浮层在用）。
2. **删「ACP · stdio」**：连同 busy 时的「agent 正在输出」，i18n key `composer.agentOutput` 两侧一并删除。理由：这行原来在说「这条通道是什么」和「agent 在输出」——前者是常量（谁都知道自己在用 ACP），后者 §21 之后已经由活动行自己说。
3. **上下文用量进工具行**：原来它是输入区上方一条独立的 `sc-glass` 卡片（`App.tsx` 里渲染），现在并进工具行左段，跟在附件按钮后面；`text-micro`（黑体，见 §24）超宽 `truncate`，**不加 Tooltip** —— 号码本身可读，悬停浮层反而挡视线；
`warn` 时 `text-warn-1`。输入区上方那条卡片删除。
4. **自动批准去玻璃态**：触发器从 `triggerVariant="control"`（`sc-control` 带 `inset 0 1px 0` 内高光 + `bg-surface-2` + 1px 边）改成 `"ghost"`，与 MCP 按钮同一种形态 —— 无底、无边、无内高光，hover 才有面。

### 23.2 为什么用量该在工具行

用量是「这一轮还剩多少余量」的静态读数，不是事件 —— 它不该在消息流与输入区之间占一整行（那一条 `mb-2 px-3 py-1.5` 的玻璃卡把输入区往上顶了 30 多 px，而信息量只有一个数字）。放进工具行后，它和「附件 / MCP / 自动批准」这些「这一轮的配置项」在同一层，语义反而更准。

### 23.3 验收（DOM 数值）

1. 外层 `border-radius` = 18px；`backdrop-filter` 含 `blur(24px)` 与 `saturate(1.5)`。
2. 工具行文本不含 `ACP`、不含 `stdio`（两种状态都查）。
3. 用量文本所在元素的 rect 在输入卡片 rect 之内；文档里不再有输入区上方那条独立用量卡（`usage.line.*` 文本只出现一次）。
4. 自动批准触发器的 `box-shadow` 为 `none`，与 MCP 按钮一致；两者 hover 前的 `background-color` 相同（透明）。
5. busy 状态下不出现「agent 正在输出」文案。

## 24. 输入框内陷底 + 用量环形读数（2026-10-29 定）

参考源：reactbits `.lh-well`（同样读自构建产物 CSS）：

```css
.lh-well{ border-radius:12px; background:var(--lh-well); box-shadow:inset 0 0 0 1px var(--lh-well-edge) }
/* 暗色 */ --lh-well: rgba(8,6,12,.3);        --lh-well-edge: rgba(255,255,255,.055);
/* 浅色 */ --lh-well: rgba(255,255,255,.62);  --lh-well-edge: rgba(24,24,27,.06);
```

**它和 §22.2「不铺实心面」不矛盾**：well 是比卡片底更深、**半透明**的一层（30% 黑），
凹槽的边靠 `inset 0 0 0 1px` 划；实心面会把 §23 卡片边缘的内边高光埋掉，半透明凹槽不会 ——
高光在卡片边上，凹槽在卡片里面，两者不在同一层。

### 24.1 改动

1. **输入框换成凹槽**：去掉 `border border-line-1`（1px 实线），改 `.sc-well`
   （`--well` 底 + `inset 0 0 0 1px var(--well-edge)`），半径 12px（`rounded-card`）。
2. **浅色主题守 §1.8**：`--well-edge` 取 `--l1`（浅色靠 1px 边框分界），不用 reactbits 的 6% 黑 ——
   6% 在浅色下等于没有边界。
3. **用量文字转黑体**：`font-mono` → 去掉（走 `--font-sans`）。理由是它是给人读的一句自然语言，
   不是需要对齐的等宽读数 —— 等宽留给代码和路径。
4. **加 18px 环**：track 用 20% 线色、fill `accent-1`（`percent ≥ 80` 转 `warn-1`）、
   `stroke-linecap: round`，中央 `Layers` 8px 图标 —— 环内径 14px，图标与环之间留 3px（10px 时只余 2px，挤）。
5. **`describeUsage` 返回值加 `percent`**：后端已算好 0–100（`UsageDto.percent`），
   前端只传不重算 —— 这行仍然不做除法。

### 24.2 验收（DOM 数值）

1. 输入框 `border-width` 为 0；`box-shadow` 含 `inset 0 0 0 1px`；`background-color` 的 alpha < 1，
   且与卡片底色不同（凹槽更深）。
2. 用量文字元素 `font-family` 不含 `mono`。
3. 环 `<svg>` 存在且 `stroke-dashoffset` 随 `percent` 变化（2% 与 82% 两个用例读数不同）。
4. 环中央有 `Layers` 图标元素。
5. `percent ≥ 80` 时环的 `stroke` = `--warn`。

### 24.3 焦点归属与工具行内缩

**聚焦框必须落在输入框自己身上**，不能由外层卡片 `focus-within` 顶替。原来的写法有两个毛病，
实测都量到了：

1. 点进输入框时亮的是**整张卡片**的 1px 边框（`focus-within:border-accent-1`），看起来像「整块控件被选中」；
2. 同时 `textarea` 自己冒出浏览器默认 outline（`outline: solid`）—— 因为 `focus-visible:outline-0`
   只管键盘聚焦，鼠标点进去不触发 `:focus-visible`，于是两层框一起出现。

改成：外层卡片不再响应 focus；`.sc-well:focus` 把自己的 inset 描边换成 `--a1`；
`textarea` 写 `focus:outline-0 focus-visible:outline-0` —— 不能用裸的 `outline-0`/`outline-none`，
样式棘轮只放行「同一 className 里带 `focus-visible:`」的写法（保留键盘焦点的语义）。

**工具行内缩与输入区取同一个值**：原来工具行 `px-2`（8px）、输入区 `p-1`（4px），
附件按钮左边缘 x=9、输入框左边缘 x=5，差 4px —— 视觉上就是「上面那行比输入框缩进去一点」。
两处统一 4px 后都是 x=5。（垂直方向本来就齐：工具行 32px 内所有子元素中心线都在 cy=17。）

### 24.4 工具行上下留白相等（不是「居中」两字能说清的那种）

所有者报「工具行视觉偏上」。量出来是：**工具行顶距卡片外缘 1px、工具行底距输入框 4px**，
差在卡片那圈 1px `border` —— 暗色下 `--glass-border` 是透明的，看不见但**照样占布局**。

三件事一起改才齐：

1. **描边改 inset 阴影**：`.sc-window` 的 `border: 1px` → `box-shadow: … inset 0 0 0 1px var(--glass-border)`。
   描边不再占布局，也不再制造 1px 的隐形偏差。这也正是 reactbits `.lh-window` 的写法。
2. **卡片必须是 `display: flex; flex-direction: column`**：否则工具行的 `margin-top` 会与父元素**折叠**，
   卡片整体被推下去、相对间距仍是 0（实测：先加 `mt-1` 后上方还是 0，加 flex 才变 4）。
3. **上下各 4px**：工具行 `mt-1`、输入区 `p-1`。

实测（暗色，卡片外缘算起）：

```
上（卡片→工具行） 4    中（工具行→输入框） 4    左 4    右 4    下 4
工具行左缘 4        卡片高 120（= 4+32+4+76+4）
```

## 25. 三个小优化：代码复制 / 事件并入诊断 / 会话计时（2026-10-29 定）

三件同一性质（可用性打磨），**同一个 PR**。共同约束：都用既有令牌与组件，不新增颜色、
不新增 arbitrary value（样式棘轮）、文案 `zh-CN.ts` / `en.ts` 两边同时改。

### 25.1 代码块的复制

- **围栏代码块**（`Markdown.tsx` 的 `pre[data-code-tokens]`）右上角出现复制按钮：
  `Copy` → 点击后变 `Check` 1.2s → 回 `Copy`；Tooltip 用既有 `ui.button.copy` / `ui.button.copied`。
- 复制的必须是**原始代码文本**（`inline.text` 拼回来的原文），**不是**高亮 token 的 DOM 文本 ——
  后者会带上省略提示与缩进差异。
- 按钮**不占布局**：绝对定位在块内右上角（块内不滚动，滚动的是 `pre` 自己，所以按钮跟块走、不跟滚动走）；
  默认 `opacity` 0.6，`:hover` / `:focus-visible` 到 1。**必须有 `focus-visible` 指示**（样式棘轮要求）。
- **行内 `code`：单击即复制**，复制后 1.2s 内换成 `Check` 图标；**用户正在选字时不抢**
  （`window.getSelection()?.toString()` 非空就只当普通点击）。
- 复制逻辑抽到 `src/lib/clipboard.ts`（`copyText()` 现在埋在 `Markdown.tsx` 里），
  **链接复制、代码块、行内 code 三处共用一份**，禁止第三份实现。
- 不复制语言标签、不复制「高亮已省略（N 行）」这类降级提示行。

### 25.2 事件信息并入诊断

- **删掉**状态栏右侧的 `EventStats` chip（`statusbar.events.short*` 的那段可见文本与它的 HoverCard）。
- 诊断浮层顶部加一行摘要：`收到 N 条事件 · 最后一条 <method>`，键沿用
  `statusbar.events.received` / `statusbar.events.last`（改的是**位置**，不是文案）。
- 状态栏不保留任何事件计数；`eventCount` / `lastEvent` 只作为诊断面板入参。
- 空事件流：摘要显示 0 条，复制按钮维持 `disabled`。

### 25.3 会话计时

- 位置：状态栏右侧，**连接状态（`ProfileStatus`）左侧** —— 即 §25.2 腾出来的位置。
- 形态：`Clock` 图标 + 等宽数字，`font-mono text-micro text-ink-3`，与 `SessionTag` 同档；
  **无 `sessionId` 时不渲染**。
- 读数：**从「本次打开该会话」起算的累计时长**。切到别的会话再切回来 → **重新起算**；
  不跨重启、不持久化、不读历史记录、不跟 ACP 会话 id 绑定。
- 格式：`< 1h` → `m:ss`（如 `3:07`）；`≥ 1h` → `h:mm:ss`。每秒更新一次（1s `setInterval`，卸载即清）。
- 悬停：Tooltip 显示「自打开起计时」+ 开始时刻（本地 `HH:MM`）。
- **它不是一个进度**：没有总量、没有倒计时、不受 `prefers-reduced-motion` 影响（数字不做动画）。

### 25.4 验收（DOM 数值，不看图）

1. 代码块：`pre` 内有复制键且 `position: absolute`，块内不含它时 `pre` 的 `getBoundingClientRect` 不变

2. 行内 `code`：有选区时点击不复制、无选区时点击复制；两档都出现 `Check` 且 1.2s 后消失。
3. 状态栏：`statusbar.events.*` 的文本节点**不再出现**在 `header` 内；诊断面板打开后有摘要且数字 === `eventCount`。
4. 会话计时：存在 `[data-session-elapsed]`，文本匹配 `^\d+:\d{2}$` 或 `^\d+:\d{2}:\d{2}$`；

## 26. 进行中计数：状态栏「N 个在跑」+ 悬停明细（2026-10-29 定）

**决定**：状态栏显示**当前有几个任务在跑**，悬停给明细。**叫「进行中」，不叫「后台」**，
并且只在**轮内**成立 —— 这是协议的边界，不是实现的取舍。

### 26.1 为什么不是「后台任务」

ACP 里没有「后台任务」这个一等公民：没有任务表、没有 `list` 方法、没有完成通知约定；
schema 里唯一一句相关注释是 *Background activity may still emit other session updates while idle*。
用「后台」命名，用户会期待一个**活过一轮 prompt** 的东西，而我们能数到的只在轮内成立：
一轮结束（`promptResult` / `promptFailed`）后不再有更新，数字必须归零。

**已核实（2026-10-29，本机 Hermes 的 ACP 适配器）**：`acp_adapter/` 里既**不发** `subagent_update`，
也**不发** `notice`。所以第一阶段**只数 `tool_call` 的在途状态**，子会话计数不做 ——
不为「可能存在」的字段预先写解析；哪天真有 agent 发，再按这一节的口径补。

### 26.2 计数口径

- 数据源：`session/update` 的 `tool_call` / `tool_call_update` 里的 `status`
  （`pending` / `in_progress` 算在跑；`completed` / `failed` 出队）。
- **按 `toolCallId` 去重**：`tool_call_update` 是增量，同一条更新一百次也只算一个。
- **跨成员**：群聊里两个 agent 各跑一个 → 2。
- **归零时机**（三处，都要实现）：① 该 agent 的 `promptResult` / `promptFailed`；
  ② `promptStarted`（新一轮开始，上一轮的残条不能带过来）；③ 切换会话 / 断开连接。
- **现有实现不能直接复用**：`useAcpEvents` 里的 `toolCalls.current[acpSid]` 只存**每个 agent 最近一条**的
  合并态（§21 的标签用它）。计数要另建一张 `acpSid → toolCallId → { title, startedAt }` 的表，
  并且**必须是 state 不是 ref**（要驱动渲染），但更新粒度是「事件到达」，不是「每秒」。

### 26.3 计时起点

`startedAt` = **客户端第一次看到这个 `toolCallId` 的时刻**（ACP 不给开始时间戳，差一个 RTT）。
文案里不许写成「工具耗时」。格式复用 `lib/session-elapsed.ts` 的 `formatElapsed()`，
**不要写第二份**。

### 26.4 位置与形态

- 状态栏右侧，**会话计时条左侧**（§25.3 那格的前面），`Loader` 图标 + 数字，`font-mono text-micro`，
  与 `SessionTag` / 会话计时同档。
- **0 个时不渲染**（不留「0 个在进行」的噪音）。
- 悬停 → **HoverCard**（不是 Tooltip：结构化、多于一行）：每行 `成员名 · title · 已跑 m:ss`，
  **按已跑时长降序**（最久的在最上，与 chip 的数字同源）。
- **列表不设条数上限**（2026-10-29 所有者定，原「最多 8 行 + 另有 N 个」作废）：
  卡片给**最高高度**、超出**内部滚动**。截断会把「最久的那条」挤掉，而它正是这个读数唯一的用处。
  - 复用 `ui/HoverCard`：它的面板已经是 `overflow-y-auto` + `pointer-events-auto`，能滚、移进卡片不关闭。
  - **高度上限要用样式棘轮允许的写法**：禁 arbitrary value。走既有间距刻度（`max-h-96`）或
    往 `styles.css` 加一个小类（`max-height: min(60vh, 28rem)`）。上限必须低于窗口高度。
- 点击 → 打开轨迹面板（与活动行右侧「轨迹」键同一入口），不新开面板。
- 文案写清「本轮内」，避免被读成全局后台队列。

### 26.5 不做

- 不做命令输出、不做日志跟随、不做 kill（那要 `terminal/*` 与进程所有权，另一个量级）。
- 不显示外部程序（如 Hermes 自己派发的 `codex exec`）的后台进程：SinceArc 是独立进程树，
  ACP 没有跨程序发现机制。**注意**：agent 若把长任务维持成 `in_progress` 的 `tool_call`，
  它就会自然出现在这个计数里 —— 这是被数到，不是客户端去探。
- 不为计数新增后端命令：纯前端从已有事件派生。

### 26.6 验收（DOM 数值）

1. 三条不同 `toolCallId` 的 `in_progress` → 计数 3；同一条再发 `tool_call_update` → 仍 3（去重）。
2. 一条 `completed` → 2；一条 `failed` → 再减 1。
3. 该 agent 的 `promptResult` 后 → 元素消失（不是显示 0）；`promptStarted` 后上一轮残条不延续。
4. 群聊两成员各一条 → 2，悬停两行、成员名不同。
5. **喂 12 条**：卡片渲染 12 行（无截断、无「另有 N 个」）；12 行不高过上限时**不出滚动条是正确行为**。
   **喂 30 条**（实测：上限 448px / 内容 684px）：`scrollHeight > clientHeight`，滚到底能看到最后一行；鼠标移进卡片不关闭。
6. 列表顺序 = 已跑时长降序；`m:ss` 每秒变化，且与 `formatElapsed` 同源。

## 27. 启动不白闪 + 发送即跳底（2026-10-29 定）

### 27.1 启动白闪：两层一起上

**决定的不是"作品味"，是把窗口创建到首帧之间那段中间态藏起来。** 白是 WebView2/原生窗口给的，
网页本身实测一秒都不白（`t=101ms` 时 body 已经是 `--s0`），所以只改 CSS 不解决问题。

两层都做（所有者 2026-10-29 定）：

| 层 | 手段 | 作用 |
| --- | --- | --- |
| 原生窗口底色 | `tauri.conf.json` → `app.windows[0].backgroundColor: "#292d3e"` | 窗口一创建就是应用底色。链路是实的：`tauri-utils` 的 `WindowConfig.background_color` → wry → WebView2 的 `SetDefaultBackgroundColor` |
| 中间态不可见 | `visible: false` + 页面加载完成后 `show()` | 用户看不到「空窗口 → 首帧」的过程 |

**实现要点（照抄，别自己发挥）：**

- `show()` 放在 **Rust 侧**的 `Builder::on_page_load`，条件是 `PageLoadEvent::Finished`
  （`tauri::webview::PageLoadEvent`）。不要从 JS 里 `show()`：那要额外的 `core:window:allow-show` 权限，
  而且前端崩在加载阶段时连调用都发不出来。
- **必须有兜底**：`setup()` 里起一个 3 秒的后台定时器，到点无条件 `show()`。
  没有它，前端任何一次加载失败都等于「双击图标没反应」。
- `backgroundColor` 只能是**静态值**（配置里），做不到跟随主题。选 `--s0` 的暗色 `#292d3e`：
  浅色主题用户首帧是暗的、然后变浅 —— 跳一次色，但不再有白。
- `index.html` 的 `html,body` 补一条内联背景（同一颜色），作为 CSS 加载前的保险；**必须内联在 `<head>`**，
  外链在 dev 模式下不生效。
- 不受 `tauri-plugin-window-state` 影响（本项目没装这个插件；装了的话它会记住 `visible` 把 `visible:false` 顶掉）。

**验收（只能真机看，视觉判定归所有者）**：双击启动，全程不出现白色；连续启动 3 次表现一致；
**故意把前端弄崩**（临时改坏 `main.tsx`）时窗口仍然在 3 秒内出现 —— 这条是对兜底的检验。

### 27.2 发送即跳底：无条件

**决定**：用户发出消息后，**无条件**滚到最底部，不管当时是不是在贴底。

为什么不是"跟随"：现有的贴底跟随是 `stickToBottom && atBottom` 两个条件
（`lib/virtual/virtual-math.ts` 的 `shouldFollowBottom`），而 `atBottom` 是滚动位置算出来的。
用户上翻读历史时发消息 → 新消息追加到尾部但 `atBottom=false` → 两个 follow effect 都不动，
**画面停在原处，自己刚发的那条看不见**；而全仓也没有「回到最新」的入口，等于没有回头的路。

**动作**：

1. `useVirtualList` 暴露 `forceScrollToEnd()`：`scrollToEnd()` + 把内部 `atBottom` 置回 `true`。
2. `sendInGroup` 在**发送成功后**调用它（成员分支与默认 agent 分支各一次）；失败路径不跳。
3. **滚两次**：调用后下一帧再滚一次 —— 虚拟列表行高是估算的，追加的那一行要等一次 measure，
   只滚一次会差几十 px。

**不做**：「回到底部」浮标（上翻时的提示）。这是另一个 UI 决定，目前不定。

**验收**：上翻到列表中部 → 发一条 → 视口在下一帧内落到最底、能看到自己那条；
停在最底部发送时视口不抖（不出现先跳后回弹）。

## 28. 插话语义：notice 呈现 + running 时三档输入（2026-10-29 定）

### 28.1 先记事实（这些是查证过的，别再重查）

| 事实 | 出处 |
| --- | --- |
| `session/update` 有 `notice` 变体（severity / title / description / `_meta`） | ACP RFD「Session Notices」，2026-10-09 稳定；schema 1.12.0 `client.rs` |
| notice 受**客户端能力门控**：agent MUST NOT 发，除非客户端 `initialize` 声明 `clientCapabilities.session.notices: {}` | 同上；不声明时协议允许 agent 用普通 agent 消息兜底 |
| 我们此前**没有声明**（`clientCapabilities` 只有 `fs` / `terminal`） | `src-tauri/src/acp/mod.rs:360` |
| Hermes 适配器在轮内收到 prompt：redirect 成功回一句文本，否则入队回一句文本，两者都 `stop_reason=end_turn` 立刻返回 | `acp_adapter/server.py:729` `_claim_turn_or_queue` |
| `StopReason` 只有 end_turn / max_tokens / max_turn_requests / refusal / cancelled —— **没有 queued/absorbed** | schema `agent.rs` |
| Hermes 的 python `acp` 是 0.9.0，**没有 Notice 实现** | venv site-packages 内 grep（只有一处无关 docstring） |
| 多声明一个能力字段不会炸握手：python `ClientCapabilities` 是 pydantic 模型，`model_config` 只设了 `populate_by_name`，多余字段默认 `ignore`；且 Hermes 的 `initialize` 根本没读 `client_capabilities` | `acp/schema.py:1372`、`acp_adapter/server.py:526` |

**结论：现在真正"没生效"的信号是一条被伪装成模型正文的英文句子。这是本节的起因。**

### 28.2 声明能力

`initialize` 的 `clientCapabilities` 增加：

```json
{ "fs": { "readTextFile": true, "writeTextFile": false },
  "terminal": false,
  "session": { "notices": {} } }
```

声明在先，呈现能力其次：将来 Hermes 升级后发 notice，我们才收得到。**不声明就永远收不到**，这是门控的方向。

### 28.3 notice 的呈现规则

- **位置**：输入区上方（composer 上沿），**不进消息流**。它是"系统在说话"，不是对话内容。
- **字段**：`severity`（`info` / `warning` / `error`，未知值按 `info` 处理）决定图标与色阶；`title` 必显；`description` 可选。
- **不落库、不进轨迹、不进历史、不参与 `session/load` 重放**（协议明确 notice 是 live event；重放里出现旧提示比不提示更糟）。
- **同类去重**：`title + description` 相同只保留一条，右上角计数 `×N`。
- **手动关闭**，**不自动消失**：这条消息的语义是"你发的东西没生效"，不能自己溜走。
- 切换会话 / 断连时清空。

### 28.4 兜底判定（agent 不发 notice 时，现在的 Hermes 就是这类）

三个条件**同时**满足才判定为"这一轮没有真正开始"：

1. 发送时本地 `busy=true`（我们自己知道本轮在跑）；
2. 该次 `session/prompt` 在 **≤400ms** 内返回，且 `stop_reason = end_turn`；
3. 从发出到返回之间，该 session **没有任何** `agent_message_chunk` / `agent_thought_chunk` / `tool_call` / `tool_call_update`。

判定的结果：这段时间里收到的文本（通常就是那句 `Queued for the next turn…`）**转成 notice 呈现**（`warning`，标题用我们的文案），
不再以 agent 气泡呈现，并按 28.6 处理原消息。

**误判边界（写清楚，不粉饰）**：真·秒答（<400ms、零工具、零思考）会被误判成"没生效"。
判定只在 `busy=true` 时生效，idle 发送永远不会走这条路径，所以最坏情况是"极快的回答被当成排队提示"。

### 28.5 running 时三档输入（Enter 默认 = 打断）

| 档 | 行为 |
| --- | --- |
| **打断（默认）** | 发 `session/cancel` → 等 `stop_reason=cancelled` → 再发新 `session/prompt` |
| **排队** | 进本地队列，显示「已排队 N 条」；本轮结束（`promptResult` / `promptFailed`）后按序发出 |
| **引导** | 走现有的 steer 路径（agent 支持 redirect 才有效） |

- 档位在输入区工具行可见（三段控件），选择落库为设置项，默认 `interrupt`。
- **打断必须有超时**：5 秒内没收到 `cancelled` → 不静默、不卡死，按 28.6 给「未发送」气泡 + 一条 notice 说明 agent 没有响应打断。
- 打断期间输入框禁用并显示「正在打断…」，避免重复提交。
- 顺序正确性：打断后的新一轮不能和旧轮的残留输出混在一起（旧轮之后到达的 chunk 属于已取消的轮，按现有轮次归属丢弃）。

### 28.6 未发送气泡（所有者 2026-10-29 定）

- 形态：消息流里一条 `role=user` 的**「未发送」气泡**，**含用户发送的原文**；与正常 user 气泡视觉可区分（警示描边 + 角标）。
- **只放内存**：不进库、重启即消失、切会话即消失。
- **原消息丢弃**：不塞回输入框、不自动重试。
- 因为不落库，天然不会进入发给 agent 的上下文；实现上也不得走任何持久化路径。

### 28.7 验收

1. Hermes 在跑时发一条（Hermes 目前只回兜底文本）→ 出现 notice 样式提示，**不是** agent 气泡；消息流里出现「未发送」气泡且含原文，输入框被清空。
2. `initialize` 带上 `session.notices` 后，Hermes 建会话/发消息一切正常（不握手失败）。
3. 切走会话再切回：notice 与「未发送」气泡都不残留；`session/load` 重放里不出现 notice。
4. 打断档：正在跑时发送 → 旧轮收到 `cancelled`、新轮开始；消息流里不出现两条 user 消息夹着旧回答的错序。
5. 打断超时（agent 不回 cancelled）→ 5 秒后出现「未发送」气泡 + 提示，界面不卡在「正在打断…」。
6. 排队档：显示「已排队 N 条」，轮结束后按序自动发出；idel 发送路径不受三档影响。

## 29. 授权框超时：本地过期 + 快照轮次（2026-10-29 定）

### 29.1 先记实测（来自 `%APPDATA%\com.sincearc.app\logs\sincearc.log`，24 次权限请求）

| 事实 | 证据 |
| --- | --- |
| 授权请求会**完全阻塞** agent：等待期内该会话零事件 | 10:32:41 请求 → 10:37:21 作答，中间 **280 秒没有任何 `forward -> webview`** |
| 我们自己最长的一次等待是 **280 秒**、另一次 **271 秒** | 日志按请求/应答配对统计（其余多在 0–70 秒） |
| agent 侧有超时，超时后自行按拒绝继续 | Hermes `acp_adapter/permissions.py:117` `resolve_permission_timeout()` → `tools/approval_context.py:305` `approvals.timeout`，**默认 300 秒**，超时记 `"… timed out after …s"` 并自动拒绝 |
| 我们没有本地计时器 | 弹框存活完全取决于 agent 何时收尾；`PermissionDialog` 只在 `expiredReason` 存在时显示过期态，而这个字段只由「轮终态 / 断连」两条路径写入 |

**结论：agent 侧超时之后，我们既不知道、也不改状态，弹框就一直挂着。**

### 29.2 「没有本轮可放行」的成因

「放行整轮」读的是**实时**映射：`App.tsx` 的 `allowTurnPolicy` 用
`acp.acpToTurn.current[activeAcpSid]` 取 turnId，取不到就抛 `50300 / "没有本轮可放行"`。
这个映射在"恢复的会话、成员会话、激活 tab 不是弹框所属会话"时都可能为空 ——
也就是说这条按钮把"我当前看到的会话"当成了"这条请求属于的会话"。

### 29.3 修法一：请求入队时快照归属

`PermissionRequest` 增加三个快照字段：`profileId`、`acpSessionId`、`turnId`（入队那一刻取值，允许为空）。
「放行整轮」只认快照，不再读实时激活态。

- 快照 `turnId` 为空 → 不报内部错误，按 29.4 的失效文案处理（"这条授权请求已失效，请重新发送"）。
- 后端 `permission_allow_turn` 仍按快照里的 profile/acp/turn 调用，不做推断。

### 29.4 修法二：本地判定 —— 惰性过期为主，300 秒兜底

**为什么不去读"真实超时"**：ACP v1 schema 里没有任何超时字段（字段级 0 处），agent 超时是**静默放弃**
（Hermes 在 `permissions.py:95` 拿到 `future.result` 超时后自己按拒绝继续，不给我们发任何东西）。
`session/request_permission` 的 `_meta` 虽是官方扩展点，但**我们是通用客户端，不为某一个 agent 的实现去读私有键** ——
那一行该由 agent 侧自己愿意加时再加，客户端不追。

两层判定（所有者 2026-10-29 定，只做这两层）：

| 层 | 判据 | 生效时机 |
| --- | --- | --- |
| **主判据：惰性过期** | 该会话在我们**尚未作答**时又出现了新事件（`agent_message_chunk` / `agent_thought_chunk` / `tool_call` / `tool_call_update` / 终态） | 立刻 —— 这是"这条授权已被 agent 丢掉"的实证，不必等满 5 分钟 |
| **兜底** | 每条请求固定 300 秒上限 | 到点 |

- 主判据的依据来自实测：等待期内 agent **完全阻塞、零事件**（一次 280 秒、一次 271 秒的空白），
  所以"又出事件了"与"这条授权还活着"互斥。
- **主判据只认同一个 ACP 会话**：群聊里两个成员各问一条时，A 干活不能把 B 的授权标死。
  快照里拿不到 `acpSessionId` 的请求一律不动手 —— 交给 300 秒兜底，宁慢不错杀。
- 两层命中后动作一致：标 `expiredReason = "permission.expiredReason.agentTimeout"`、从队列移除、
  弹框转过期态（复用 `PermissionDialog` 的过期分支）、发一条 `warning` notice、写 `PERM-EXPIRE` 日志。
- 计时器在作答、轮终态、断连、卸载时清除（不要让兜底逻辑盖掉真实结果）。
- **取舍（写清楚）**：300 秒是对齐 Hermes 默认值（`tools/approval_context.py:305`），不是读来的真值。
  有人把 agent 超时调大时我们会提前判定过期 —— 代价是重发一次消息；调小则我们晚标几秒，无害。
  主判据把绝大多数情况从"等 5 分钟"缩短到"几十秒"，兜底只负责没有后续事件的死场景。

### 29.5 修法三：作答失败不再静默

用户点关闭/允许/拒绝时，若 agent 已经不等这条请求（自动拒绝 / 轮结束）：

- 请求标成过期态并说明原因（agent 已超时 / 这一轮已结束），**不弹内部错误码**；
- 写一条诊断日志（`PERM-STALE`），并在诊断面板可见；
- 关闭弹框本身仍然**必须发出应答**（现状 `onCancel → decide(null)` 是对的，保持）——
  不答会让 agent 一直阻塞到它自己的超时，界面表现为"关掉之后什么都没有"。

### 29.6 诊断日志四条（现在只有失败才记）

权限请求生命周期各打一条：`PERM-ASK`（到达，含 id/kind/是否有 turnId）、`PERM-ANSWER`（作答，含 outcome/耗时）、
`PERM-EXPIRE`（原因）、`PERM-STALE`（作答被拒）。带耗时，下次这类问题看日志就能定位，不必再靠猜。

### 29.7 验收

1. 弹框挂 300 秒不操作 → 自动转过期态并出现 notice；再点任何按钮**不报 50300**。
1b. **惰性过期**：请求未作答时该会话又出现事件 → 弹框**立刻**转过期态（不必等满 300 秒）；
   作答后再来的事件不得误触发（作答成功即清掉判据）。
2. 「放行整轮」在恢复的会话 / 成员会话里可用（用快照 turnId），不再依赖当前激活 tab。
3. 关掉弹框 → agent 立刻收到应答（日志有 `PERM-ANSWER`），后续动作继续进来。
4. 正常点击（<300 秒）行为不变：一次作答、一个 `PERM-ANSWER`、没有多余 notice。
5. 轮终态 / 断连导致的过期仍然照旧（新计时器不得覆盖这两条路径）。

## 30. 单例启动（2026-10-29 定）

### 30.1 为什么不是观感问题

没有单例保护时，多开的代价是实打实的：

- 两个进程同时打开同一个 `sincearc.db`（`%APPDATA%\com.sincearc.app`），SQLite 写冲突不可控；
- 每个实例各起一套 ACP agent 子进程，同一份历史里两条会话互相踩；
- 两个 updater 同时检查/下载更新；
- 「点了没反应 → 再点一次」是最常见的重复启动来源，现在会真的开出两个窗口。

### 30.2 做法

`tauri-plugin-single-instance`（v2 线，本次解析到 **2.5.5**）：

- **必须是 `Builder` 上第一个注册的插件**。晚于其他插件注册，第二个实例可能在拿到锁之前已经把窗口/数据库初始化过一轮。
- 第二个实例的行为：把已有窗口 **`unminimize()` → `show()` → `set_focus()`**，然后自己退出。
  只 `set_focus()` 不够 —— 窗口最小化时 focus 不会把它还原。
- callback 里**不做重活、不 panic**：它跑在第二个实例的进程上下文里，panic 会表现成「双击图标没反应」。
- 窗口 label 用默认 `main`（`tauri.conf.json` 的 `app.windows[0]` 没写 label）。
  锁的键来自 `identifier = com.sincearc.app`：Windows 是命名 mutex。
- **不转发 CLI 参数**：当前没有「用某个目录/文件启动」的语义，第二个实例的参数直接丢弃；
  等 E14（项目与位置）落地后若要做「再次启动打开指定项目」，再扩 callback 的 `args`。

### 30.3 已知坑

1. **dev 与 release 共用同一把锁**（同一个 identifier）：调试时如果打包版开着，
   `npm run tauri dev` 会被顶掉或顶掉别人，表现是「窗口没起来但进程退了」。调试前先 `taskkill /IM sincearc.exe /F`。
   要给 dev 单独的 identifier 得改一份 config，本卡不做。
2. **更新器重启路径必须验**：`tauri-plugin-updater` 重启时旧进程先退、锁才释放；
   旧进程没退干净的话，新进程会等约 10 秒再退出，用户看到的是「点了更新没反应」。
3. 与 `visible: false`（§27.1）叠加时：第二个实例的 callback 里 `show()` 会直接显示第一个实例的窗口 ——
   这正是想要的，不需要额外判断"是否已加载完成"。

### 30.4 验收

1. 开一个实例 → 再双击图标：**不出现第二个窗口**，已有窗口还原并到前台（最小化状态也成立）。
2. 任务栏再点一次、开始菜单再点一次：行为同上。
3. 更新器「重启」之后仍只有一个进程（`tasklist | findstr sincearc` 只有一行）。
4. 任务管理器里始终只有 **一个** `sincearc.exe`；`sincearc.db` 没有被两个进程同时打开。

## 31. agent 回复完成的通知（2026-10-29 定）

### 31.1 决定

| 项 | 定论 |
| --- | --- |
| 触发点 | **一轮结束**（`promptResult` 且 `stop_reason = end_turn`）；用户主动取消/失败不响 |
| 音效 | **内置音频资源**（我们自己合成，不用系统提示音） |
| 聚焦且正在看该会话 | **不打扰**（三分法的第三档） |
| 便携版 | **只发音频**（不发系统通知、不闪任务栏） |

### 31.2 三分法（按窗口焦点与当前会话）

| 状态 | 行为 |
| --- | --- |
| 窗口未聚焦 / 最小化 | 系统通知（尽力）+ 音效 |
| 窗口聚焦，但正在看的是**别的**会话 | 只音效 |
| 窗口聚焦，且正在看**这个**会话 | 都不做 |

判定用窗口自己的焦点状态（`is_focused`）与当前激活会话 id，不看"上次活动时间"那类猜测。

### 31.3 音效

- 资源：`src/assets/notify-reply.wav`（16-bit / 44.1kHz / 单声道，≤0.8s，峰值压到约 −11 dBFS）。
  **定稿为候选 A**：D5(587.33Hz) → A5(880Hz) 纯五度上行，低八度垫底，0.75s。
  合成参数留档在 `~/.hermes/cache/scratch/sfx/gen.py`（正弦 + 泛音 + 指数包络，软起音、20ms 尾部淡出）。
- 播放：webview 里一个常驻 `Audio` 对象，`currentTime = 0` 后 `play()`；失败（自动播放被拦）静默降级并写一条诊断，**不弹错误框**。
- 可以关：设置里「回复音效」独立开关，默认开。
- 音高/时长/音量可调，但**不做"音量滑杆"**：只有开/关，避免多一个要维护的偏好。

### 31.4 系统通知

- 用官方 `tauri-plugin-notification`。
- **Windows 上只对「安装版」可靠**（官方文档：Only works for installed apps）。便携版几乎一定会被系统静默丢弃 ——
  所以失败时的行为是**静默降级为只发音频**（所有者 2026-10-29 定：便携版仅发送音效，不闪任务栏）。
- 标题固定为应用名，正文是该轮回复的首行摘要（截断到 ~120 字，去掉 markdown 标记的换行）。
- 点击通知的回焦是 **best effort**：Windows 上只有 toast 还在屏幕上时才报点击，进通知中心之后不报。
  能回焦就回焦并切到该会话；不能就什么都不做，不假装成功。
- 可以关：设置里「系统通知」独立开关，默认开。

### 31.5 节流

- **一轮只响一次**：判据是 `promptResult` 事件本身，天然一回一次。
- 同一时刻多个会话结束：**合并成一次**（音效只放一次；系统通知只发最后一条，正文带"N 个会话已完成"）。

### 31.6 验收

1. 窗口在前台、正在看该会话 → 一轮结束**无声无通知**。
2. 窗口在前台、切到别的会话 → 只听到音效，没有系统通知。
3. 窗口失焦（或最小化）→ 系统通知出现 + 音效；安装版成立，便携版只有音效。
4. 用户点停止（`cancelled`）或这一轮失败 → **不响**。
5. 关掉两个开关 → 都不响；只关音效 → 通知照发；只关通知 → 音效照放。
6. 两个会话几乎同时结束 → 音效只放一次。

## 32. agent 自发起的轮（2026-10-29 定）

### 32.1 现象与实证

后台任务（如 `terminal(background=true)` 跑 Codex）结束时，agent 会被唤醒继续干活，但界面**完全没反应**。

`sincearc.log`（UTC，晚上那次）：

```
11:43:11.747  forward -> webview kind=promptResult                     ← 上一轮正常结束
11:47:25.860  forward -> webview kind=notification:session/update ×367 ← 唤醒后的整轮，367 个事件
              （其间没有 promptStarted，也没有 promptResult）
11:53:07.070  forward -> webview kind=request:session/request_permission
```

事件全都到了 WebView，界面上一个字都没有。

### 32.2 根因

`promptStarted` 只在客户端发起 `session/prompt` 时产生（`commands.rs` 的 `sessionPrompt` 分支）。
agent 被唤醒这一轮**不是客户端发起的**，Agent Client Protocol 里也没有对应的「轮开始」消息 ——
服务端直接推 `session/update`。

前端收到 `agent_message_chunk` 时用 `shouldAcceptChunk(inFlight, lateUntil, now)` 过滤：

- `inFlight` 在上一轮 `promptResult` 时清掉，此刻为 `false`；
- `lateUntil` 是 `session/load` 之后的重放窗口，此时早过期。

于是**每一块都被当成重放丢弃**（诊断里是 `DROP-REPLAY`，367 次），界面不进生成态、不显示正文；
也没有 `promptResult`，所以「进行中」不归零、计时不收尾、§31 的回复通知也不会触发
—— 通知功能的触发点正是 `promptResult`，这个场景下它根本不存在。

### 32.3 做法：由 Rust 侧合成轮边界

判定权只可能在 Rust：只有它知道「客户端此刻没有未决的 `session/prompt` 请求」。

1. **轮开始**：某 ACP 会话**无未决 prompt 请求**，却收到 `session/update`（正文或工具调用）
   → 判定为 agent 自发起，先合成 `PromptStarted`（新 `turn_id`，`origin: "agent"`），再转发原事件。
2. **轮结束**：同时满足三条才合成 `PromptResult { stop_reason: "end_turn", origin: "agent" }`：
   - 该会话连续 **8 秒**没有任何事件（`AGENT_TURN_IDLE_MS = 8_000`）；
   - 没有 pending / in_progress 的工具调用（§26 那套判据）；
   - 没有未作答的授权请求（§29 那套判据）。
3. 客户端发起的正常轮**行为完全不变**：有未决 prompt 请求时，原始 `promptStarted` / `promptResult` 照旧，
   合成逻辑一步都不介入。

### 32.4 `origin` 字段

`PromptStarted` / `PromptResult` 增加 `origin: "client" | "agent"`（缺省 `client`，向后兼容）。
用途：诊断与轮次列表可以标出「这轮不是我发的」；界面暂不加视觉标记（等真需要再说）。

### 32.5 为什么可以接受「静默推断」

- 协议没有结束信号，静默是唯一可用的近似；
- 两个 busy 守卫挡住了大多数误判：长工具调用期间有 pending tool call，等待授权期间有未答授权请求；
- 真误判（长思考、无工具、>8 秒）的后果是**提前收尾**，后续 chunk 会再开一轮 ——
  表现为多一条轮次记录，**内容不丢**，也不影响本轮的持久化。

### 32.7 实现与排查

机制、代码位置、判据来历、症状对照表、止血手段见 **`docs/acp-turn-synthesis.md`**（出问题先读它）。

### 32.6 验收

1. 后台任务唤醒后：界面**立刻**进入生成态，正文、工具调用、进行中计数全部照常；
2. 这一轮结束后：生成态退出、计时收尾、§31 的回复通知按三分法触发；
3. 客户端自己发的轮：行为与现在完全一致（`promptStarted` 与 `promptResult` 仍来自真实请求）；
4. 自发起轮期间等授权（>8 秒无事件）：**不**被判结束，直到作答后继续；
5. 长工具调用（>8 秒无事件）：**不**被判结束；
6. 诊断里能看到合成的轮边界（`TURN-SYNTH-START` / `TURN-SYNTH-END`，带 turnId 与原因）。

## 33. 消息列表：高度元数据 + 滑动窗口（2026-10-29 定）

### 33.1 先看实测

探针：`probe-vlist.html`（`src/probe-vlist.tsx`），同一页面同一份数据，Chromium headless，
滚动 120 帧 × 60px，消息 30% 含代码块/表格：

| 条数 | estimate 缓存 | p50 帧 | p95 帧 | 最大帧 | estimate 调用/帧 | estimate 总耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| 500 | 否 | 16.7 | 16.8 | 16.8 | 238 | 137 ms |
| 2000 | 否 | 16.7 | 16.7 | 16.8 | 1050 | 450 ms |
| 5000 | 否 | 16.7 | 16.8 | **33.3** | 2675 | **1076 ms** |
| 5000 | **是** | 16.7 | 16.7 | 16.8 | 2675 | **0 ms** |
| 20000 | 否 | **49.9** | **83.4** | **100** | 10800 | 4128 ms |
| 20000 | **是** | 16.7 | 16.8 | 16.8 | 10800 | 0 ms |

两条结论：

1. **`estimateSize` 每帧被调 O(n) 次**（virtualizer 为算总高，对未测量项逐个调）。这个调用本身便宜；
   贵的是 `message-height.ts` 里对含 ``` / 表格的消息**真去 `parseMarkdown`** —— 5000 条时 120 帧做了 96,273 次解析。
2. **只把 estimate 结果缓存，20000 条也不再掉帧**（p95 83.4 → 16.8）。所以这是第一因；
   滑窗的作用是把 O(n)/帧 压成常数、并控制内存，不是"掉帧的唯一解"。

边界：探针的行是简化行（`pre-wrap` 纯文本），真实 `MessageItem` 还要渲染 markdown/代码块/按钮，
所以这张表只代表"estimate 这条链"的份额，不代表整体帧时间。

### 33.2 高度元数据：estimate 只许查表

- 每条消息的"大概多高"**只算一次**：优先用 `atomKind`；没有时再看正文是否含块语法（``` / ~~~ / ![ / 表格）。
- 结果缓存在内存里（按消息 id），**不改数据库 schema**：这是渲染优化，不是数据模型的一部分。
- `estimateMessageHeight` 的契约改成「查表 + 未命中时算一次并写入表」，**禁止在热路径里解析 markdown**
  （代码评审铁律：这个函数每帧被调 O(n) 次）。
- `estimate` 回调的**函数身份必须稳定**（依赖空数组，从 ref 读当前消息数组）。
  现状 `App.tsx` 里依赖 `[state.msgs]`，流式正文每来一段就换身份，虚拟器会把测量缓存全作废。

### 33.3 滑动窗口

- 窗口 `MESSAGE_WINDOW = 200`，滞回：`state.msgs.length > 250` 才裁，裁回 200。
- 窗口**跟着视口滑动**：视口靠近上沿就裁尾部，靠近下沿就裁头部；不靠近任何一边时不动。
- **永不裁**：正在流式的消息、未发送气泡、被引用的原消息、正在跑的 turn 的消息。
- 双向回填：
  - 向上：视口进入前 30 条 → 复用已有 `loadOlder()`；
  - 向下：视口进入后 30 条且 `trimmedTail` → 新增 `loadNewer()`（DB 侧按 `seq > ?` 正序取一页）。
- 状态语义要分清三个，不许混用：
  - `hasMore`：**数据库里还有更早的**（现在就有）；
  - `trimmedHead`：**内存里更早的被裁掉了，可以回填**；
  - `trimmedTail`：**内存里更新的被裁掉了，可以回填**（只有向上滚很远才出现）。
- 引用降级：被引用消息不在窗口里 → 显示「更早的消息」占位，不显示空白、不报错。
- 滚动锚定：裁剪必须补偿 `scrollTop`（复用 `beginAnchorShift` / `endAnchorShift` 那套，方向相反）。
- 跳转到某条消息（`scrollToMessageIndex`）目标不在窗口内时：**不做无意义跳动**，写一条诊断并放弃。

### 33.4 门槛（验收就用探针量）

1. 5000 条、30% 块语法：滚动 p95 帧 ≤ 20ms；**estimate 调用/帧不再随总条数增长**（≈窗口量级）；
2. 20000 条：同上（窗口生效后 p95 ≤ 20ms）；
3. `state.msgs.length` 稳态 ≤ 250；
4. 上滚 500 条历史再滚回来：不跳位、不重复、不丢正在流式的消息；
5. 裁剪/回填全过程贴底跟随（§27.2）与强制跳底行为不变。

### 33.5 明确不改

- 落库格式、消息 id、`seq` 语义、`messagesAppend` 的合并规则；
- 贴底跟随与发消息强制跳底（§27.2）；
- `loadOlder` 的触发位置（顶部附近）与 `hasMore` 的含义。

### 33.6 探针留在仓库

`probe-vlist.html` + `src/probe-vlist.tsx` 作为可重复的压测入口保留（不参与正式页面），
用法：`npm run build` 后起静态服务访问 `/probe-vlist.html?n=5000&md=0.3&cache=0`。

### 33.7 修订：裁剪的竞态与 pin 过宽（2026-10-29 晚间实测反馈）

上线 0.0.7 后出现两个问题，都是 33.3 的实现缺陷，不是设计错方向：

**① 滚到底不裁** —— `pinned` 把「被引用的原消息」也放进去了。`planWindow` 收缩边界的方式是
「pinned 落在裁剪区间内 → 边界收到 pinned 之前」，于是会话里只要**任何位置**有一条引用，
它的下标就会把 `dropHead` 从几百压到接近 0，等于永不裁剪。这与 33.3 里「引用被裁 → 显示『更早的消息』」
的降级设计自相矛盾：有前者，后者永远用不上。

**② 向上翻阅时滚条跳回底部** —— 裁剪会同时改 `scrollHeight` 与 `scrollTop`，而贴底跟随的判据
`atBottom = scrollHeight - scrollTop - clientHeight <= 8` 是在**变化中途**采样的：

```
裁剪 → scrollHeight 骤减 → 浏览器把 scrollTop 夹到新 max
     → 这一刻差值 ≤ 8 → atBottom 被判为 true → 贴底跟随 effect 触发 scrollToEnd()
```

裁尾时 `use-trim-anchor` 还把 `scrollTop` 夹进 `[0, max]`，正好制造这个瞬间。
另外 `endAnchorShift` 在锚点行被裁掉时会回退到 `index 0` 并 `scrollToIndex`，同样是一次跳。

修订后的规则：

1. **pin 只保留两样**：正在流式的消息、未发送气泡。「被引用的原消息」不再 pin（用占位降级）；
   「运行中 turn 的消息」只在**末尾 60 行内**才 pin —— 历史里若有状态卡住的 turn，不许它压住窗口边界。
2. **程序化滚动不许改 `atBottom`**：裁剪与锚点补偿期间置标记，该窗口内的 scroll 事件不得把
   `atBottom` 置为 `true`；`count` / `totalSize` 变化只允许据此**置 false**，不许置 true。
3. **锚点行被裁时不做 `scrollToIndex`**：`endAnchorShift` 找不到锚点 key 时只清状态，位置交给裁剪补偿。
4. **裁剪与锚点互踩**：锚点补偿未落定时，`useTrimAnchor` 跳过本次裁剪（延后一帧再算）。
5. **留痕**：`WINDOW-TRIM head=N tail=N top=… h=…`、`WINDOW-PIN-SHRINK plan=…→…`、
   `WINDOW-ANCHOR-LOST`、`FOLLOW-END reason=…` 四条诊断，出问题直接读日志，不再靠猜。
## 34. 思考行图标居中 + 运行中发送模式全局化（2026-10-29 定）

### 34.1 思考行头部图标垂直居中

现状是"手调偏移"：头像用 `mt-0.5` 往下推、三点容器用 `items-end`、定位按钮里的 `Waypoints` 直接落在

1. 前置指示器（running 的品牌 loader、历史的三个点）统一包进**固定尺寸盒**：

4. 顶部名字行的头像：`mt-0.5` 手调改 `self-center`（让它跟着行盒中心走，而不是猜一个像素）。

`busyInputMode`（打断 / 排队 / 引导）本来就是**全局的单一份设置**（Rust `AppSettingsDto.busyInputMode`，

- **加到** 设置 → Chat 区，作为一项全局偏好（`settings.busyMode.label` + `.hint`），选项文案沿用现有三条；

## 36. 代码页：添加项目改成选择器（2026-10-30 定）

现状是**手输一个路径**（`sidebar.projects.add` 展开一个输入框）。问题是：用户手上通常只有
「GitHub 上那个仓库」，路径是它的下游事实 —— 让人先自己找路径再加，等于把「克隆/定位」的活推给他，
而且加完仍无身份（`useRepos` 是纯 React state，重启就没了，`slug` 是占位）。

### 形态

点「添加项目」展开的是一块面板（就地展开，不是模态），三段并列：

```
┌ 添加项目 ────────────────────────────┐
│ 从 GitHub        [ 搜索 / 最近使用 ]   │
│   ▣ wangsyiiz/SinceArc   已有副本      │  ← pin 区，带标记
│     acme/api             只看不干      │
│     acme/web             需 clone      │
│   ── 最近 ──                          │
│ 本地目录                               │
│   ~/source/sincearc        [ 添加 ]    │  ← 手输/粘贴，仍保留（L3 兜底）
│   ⓘ 目录的 origin 决定它归到哪个项目     │
└───────────────────────────────────────┘
```

- **从 GitHub**：`gh repo list`（`gh.md §2.2` 的契约）。每行右侧标出与本地的关系三态：
  `已有副本`（L0 命中，可直接用）/ `需 clone`（远端有、本地无）/ `只看不干`（远端有、明确不落地）。
- **本地目录**：仍然保留手输（拖目录进窗口也算）。加进来时用 `resolve_repo()` 解析 origin；
  解析不出远端就明确说「这个目录没有 remote」，而不是静默建一个无名项目。
- **pin**：列表可 pin，pin 在 `repos`（远端身份）上，不是本地副本 —— 同一项目换副本不该掉 pin。
- **排序**：pin 区（`pinned_at DESC`）→ 最近（`last_used_at DESC`）→ 其他（`name`）。
- **不预选、不记忆当前项目**（E14 原则）；pin 是显式动作，允许持久。

### 必须一起做的三件小事

1. **GH 不可用不隐藏入口**：`gh` 没装/没登录时，「从 GitHub」这一段显示原因（沿用 `GhStatusDto`），
   但「本地目录」照常可用 —— 不许整块消失。
2. **来源可见**：项目行上要能看出它从哪来（`GH` / `本地`），否则用户不知道"为什么有的能看 PR 有的不能"。
3. **失败不静默**：`clone` 与"只看不干"都必须有明确结果反馈，并写一条诊断
   （`REPO-CLONE-FAIL` / `REPO-REMOTE-MISSING` 之类），不许只吞掉。

### 与既有卡片的关系

- E14.1（项目落库）是本节的前置：没有 `repos` / `local_repos`，pin 与最近都无处存；
- E14.2（新建会话选择器）复用同一份列表，但**不在本次范围**（本次只做代码页的添加/管理）；
- `docs/gh.md §2.2` 定义数据来源与契约，本节只管界面表达。

## 37. 标题栏右侧的 GitHub 身份（2026-10-30 定）

三个窗口按钮（最小化/最大化/关闭）是我们自己画的（`decorations: false` + `TitleBar.tsx`），
所以「按钮左侧插一个头像」是纯前端布局，不涉及原生标题栏。

### 形态

```
[品牌] SinceArc   ● hermes · 本机 · ~/source    (avatar) [—][□][×]
                                                  ↑ 18px 圆 + 4px 间距
```

- **有登录**：18px 圆头像（`avatar_url`），hover 出 login（自研 `ui/Tooltip`，不用原生 `title`）；
  点击暂不做动作（跳浏览器是后续可选项，不是本次）。
- **gh 没装 / 没登录**：同一个位置显示 **「未登录」** 小字（`text-micro text-ink-3`），点击无动作。
  空白是不行的 —— 位置固定，不然标题栏右边会忽宽忽窄。
- **取身份失败（超时/网络）**：**什么都不显示**，也不写「未登录」。把网络问题说成"没登录"会误导排查。
- 头像加载失败（图片 404 / 被墙）→ 退化成 login 首字母圆形占位，不留破图图标。

### 时序

- **窗口打开后异步取一次**，不参与首帧：身份不是可用性前提，晚 1 秒到没影响；
- 进程内单例缓存（模块级 promise），切标签/重挂载不重复请求；Rust 侧另有 1h TTL；
- 取不到就用「未登录」/ 空，不重试轰炸（失败后本次会话不再自动重取，只能靠重启）。

### 边界

- 头像来自 `avatars.githubusercontent.com`（实测 200 / 0.59s，与 `github.com` 主站的 TLS 问题无关）；
- 现在 `tauri.conf.json` 没有配 CSP，所以外链图片能直接加载；**将来若加 CSP，必须放行
  `img-src https://avatars.githubusercontent.com`**，否则头像会静默消失。
- 头像与 login 属于「本机 gh 的登录态」，不落我们自己的库（重启由 gh 自己回答）。

### 36.1 修订：添加项目改成弹窗（2026-10-30）

§36 原来是「就地展开面板」。实测不行 —— 面板长在侧栏里，**展开就把项目列表顶掉**，
而且添加项目是低频动作，却占着高频列表的位置。改成：

- **触发**：项目区底部一个控件，与「新建会话」**同一套样式**（`sc-control` + `Plus` + 文案 + 右对齐提示），
  点击打开弹窗；不再有"就地展开"。
- **弹窗**：复用 `ui/Dialog`（原生 `<dialog>` + `showModal`，宽度 `md`），标题「添加项目」，
  Esc / 点遮罩关闭。列表在弹窗内有自己的最大高度 + 内部滚动，不让弹窗撑满屏。
- **内容不变**：三段（从 GitHub / 本地目录 / 三态 + pin）、三态标记、错误就地显示、键盘 ↓↑/Enter。
- **列表不被遮挡**：弹窗是覆盖层，关掉之后侧栏项目列表原地不动（这是这次改形态的唯一目的）。

为什么低频用弹窗、高频用轻控件：新建会话一天几十次，模态是它的敌人；添加项目一周一两次，
模态反而能把"从 GitHub 挑还是填本地路径"这件需要专注的事说清楚。

## 38. 会话切换时的视图状态：滚动位置与草稿（2026-10-30 定）

切会话过去的实现只有一件事在变：`lastSessionId` 换了，右侧那棵常驻树换数据。带来两个 bug（都是所有者实测）：

1. 会话一的滚动条停在 10%，切到会话二还在 10% —— 滚动容器 `scrollRef` 是同一个 DOM 节点，没人复位；
2. 输入框里打了一半的字跟着到了另一条会话 —— `Composer` 的 `value` 是组件内 `useState`，没按会话分桶。

这两条按 `docs/data-plane.md §3` 的口径都是 bug：**切换后任何一个位置还在显示上一条会话的数据就是 bug**。

### 38.1 决定

- **滚动位置按会话记忆并恢复**（所有者 2026-10-30 定：恢复，不是回底部 —— 否则未读跳转没有意义）。
- **草稿按会话保留**：切回来字还在；remount 不许把它清掉。
- **其余局部状态一律重置**：hover 卡片、mention / slash 菜单、轨迹面板的定位高亮都不跨会话。

### 38.2 口径

- 锚点 = `{ messageId, offsetTop }`：`offsetTop` 是该消息相对滚动容器顶部的真实偏移（可为负）。
  换算复用 `src/lib/virtual/virtual-math.ts` 的 `anchorTargetScrollTop()`，不许另写一套。
- 恢复时机：mount 后等虚拟列表完成一次 measure（下一帧），按 `messageId` 找 index 再摆位。
  **找不到锚点就退到底部**（消息有滑动窗口裁剪，长会话的锚点可能已被裁掉）—— 不许停在 0、不许留白。
- 存储：会话切走时写、切回时读；必须在内存里也行，但必须按 `uiSid` 分桶，不许用全局单值。
- 草稿同样按 `uiSid` 分桶；发送成功后清该会话的草稿。
- remount 边界：聊天区（消息流 + 输入区）挂 `key={lastSessionId}`，把组件局部状态强制归零；
  状态栏 / 侧栏 / 标题栏不在 key 内（它们的数据本来就按 `uiSid` 取）。

### 38.3 验收

- 会话 A 滚到中间 → 切 B → 回 A：位置一致（误差 ≤ 1 行高）；B 从自己的位置开始。
- A 打一半字 → 切 B：B 输入框是空的 → 回 A 字还在。
- 长会话（窗口已裁剪）锚点丢失时落到底部：不报错、不停在顶部。
## 39. 标签栏：最小宽度、溢出菜单与 pin（2026-10-30 定）

**现象**（所有者实测）：标签一多，标签被压到比内容还窄，关闭按钮溢出到相邻标签上、互相压字。
原因：容器 `overflow-x-auto`，每个标签只有 `max-w-55`、**没有 min-width 也没有 shrink-0**，
flex 默认可压缩 —— 压缩发生在标签内部，`shrink-0` 的关闭按钮就顶出去了。

### 39.1 决定

- 每个标签有**最小宽度** 120px（`--tab-min-w`，见 `design-language.md §13`），组件加 `shrink-0`；
  标签栏容器**不再横向滚动**。
- **可见数量由容器宽度算出来**，不靠 CSS 猜：`ResizeObserver` 量容器，按
  `floor(width / (minW + 分隔))` 定能放几个；**pinned 与 active 必须可见**，其余按顺序进溢出。
- 溢出标签收进**标签栏最右侧固定的下拉按钮**，菜单里用同一个标签组件（第二份实例，样式与行为一致）。
- **pin**：按钮在关闭按钮左侧（hover 同组出现），pin 住的标签排在标签栏最左、彼此保持原顺序；
  pin 状态持久化（`localStorage` 键 `sincearc.tabs.pinned`），启动按 pinned 顺序先重建。
- 溢出菜单里的标签同样能 pin / 关闭 —— 不许出现「菜单里点不动」的第二套行为。

### 39.2 口径

- 宽度阈值只许写成令牌（`design-language.md §13`），组件里不许出现裸 `120`。
- 可见性判定抽成纯函数（`fitTabs({ width, minW, gap, tabs, pinned, activeId })`）并单测，
  不要在 JSX 里 `if` 出没人能测的边界。
- active 即使排在后面也必须可见：优先保 active，其次保 pinned，最后按原顺序填满。

### 39.3 验收

- 连续开到第 n+1 个标签：最后一个进溢出菜单；标签栏无横向滚动条、无叠字、关闭按钮都在自己的格子里。
- pin 两个标签：固定在最左且顺序与 pin 先后一致；关掉再开仍在最左。
- 重启应用：pinned 按顺序重建，其余不自动重开（与 §3.6「自动打开只做一次」一致）。

### 39.4 口径补充：标签宽度固定（2026-10-30 实现时定）

「能放几个」要算得准，标签宽度就必须是**确定值**：每个标签固定 `width: var(--tab-min-w)`（不再随标题变宽，
原先的 `max-w-55` 已去掉），标题超出截断。否则长短不一的标签会让「按最小宽度算出的可见数量」偏乐观，
最后一个仍被容器裁掉 —— 那正是这次要消灭的叠字。

副产物：pin 与溢出菜单的取舍变成可推理的（`fitTabs` 的容量判据与实际宽度一致），单测才有意义。

## 40. 会话标题的来源与优先级（2026-10-30 定）

**现状**：标题只有一个来源 —— 首条用户消息落库时 `set_title_if_unnamed()` 截一段（`commands.rs`）。
ACP 侧的标题被完全丢掉：`session_info_update` 收到就丢，`session/list` 也没用。

**协议侧能力**（`agent-client-protocol-schema 1.12`，逐条查过）：

| 入口 | 有 title | 说明 |
| --- | --- | --- |
| `session/new` 响应 | 否 | 只有 `sessionId` / `modes` / `configOptions` / `_meta` |
| `session/update` → `session_info_update` | 是 | `title` / `updatedAt`，可 null 清空；本机 hermes 适配器在**回合开场自动起标题后就推**这条 |
| `session/list` | 是 | `SessionInfo.title`，需 agent 广告该能力 |

### 40.1 决定

- **agent 推的标题优先**（所有者 2026-10-30 定）。
- **首条用户消息是兜底**：不推标题的连接也必须有个名字。
- **暂不做用户改名**（预留来源值 `user`，本批不实现）。

### 40.2 口径

- `sessions` 加 `title_source TEXT`（取值 `'user_msg'` / `'agent'` / `'user'`；老行初始 `'user_msg'`）。
- 覆盖规则：`agent` 可以盖 `user_msg`；`user_msg` 不许盖 `agent`；`user` 谁都不许盖（本批无写入方）。
- `session_info_update.title` 为空 / null → **忽略**（清空标题会把侧栏变成空白，不是我们要的语义）。
- 同一标题重复推送要幂等（幂等按值比，不比时间戳）。

### 40.3 验收

- 用会推 `session_info_update` 的连接（本机 hermes）新建会话并发一条：标题在 agent 起完标题后更新，
  且重启应用后仍是 agent 给的那个；断掉 agent 标题能力（或用一个不推的连接）时仍是首条用户消息。

## 41. 侧栏会话列表项（2026-10-30 定）

**现状**：标题 / 成员色点 / `cwd` / 右侧连接名徽标；执行态只在「更多」菜单里当禁用条件用。

### 41.1 决定（所有者逐条指定）

  2026-10-30 所有者改：原「内联在标题行尾」作废 —— 未读变多时会把标题挤短，且与标题右侧的
  loading 抢同一格；贴右下角后，右边缘自上而下是 `⋯` 按钮 / 未读数，两个都是「行级状态」，互不打架。

## 42. 未读计数与跳转（2026-10-30 定）

### 42.1 决定（所有者口径）

- **系统提示也计入未读**；**跨重启保留**。
- 打开会话时若还有未读：消息流与输入框之间给一个**浮动按钮**，点击跳到第一条未读位置；
  到达后计数清零。

### 42.2 口径

- 数据源只认库，不认内存：`sessions.last_read_at INTEGER`（**毫秒**，与 `atoms.at` 同单位；
  `sessions.created_at` 是秒，别混用）。
- 未读数 = `count(atoms where session_id=? and channel='chat' and role in ('player','system') and at > last_read_at)`。
- `sessions_list` 的 `SessionRow` 增加 `unread_count: number`；新增命令 `session_mark_read(sessionId)`：
  把 `last_read_at` 推到「当前最新 chat 原子的 at」（不是 `now()` —— 否则打开期间新到的消息会被顺手读掉）。
- 跳转位置由前端在打开会话那一刻定格（首条未读的 messageId），**不许**每次渲染重算。
- 浮动按钮文案带条数；滚动到该位置或点击后：清 `unread_count`、写 `last_read_at`。
- 消息滑动窗口会裁掉老消息：目标已不在窗口里时，先 `loadOlder` 逐页找，找不到就退到底部并清计数（不许卡住）。

### 42.3 验收

- 两个会话：在 A 里让 agent 跑完，切到 B，A 的未读数为 1；重启应用后仍是 1；打开 A 后归 0。
- 未读跨多条时按钮显示条数，点击落在第一条未读上（不是最后一条、不是底部）。

## 43. 主区的渲染分派：路由 + Outlet（2026-10-30 定）

**问题**：`src/App.tsx` 已到 3000 行，其中 `main` 里靠四段
`{activeTab?.kind === "session" && …}` / `"repo"` / `"settings"` / `"pr"` 内联分支决定渲染谁。
每一段都直接从 App 的局部变量闭包里取十几到几十个值 —— 想改其中一块，必须先读懂整个 App。

**这不是 bug，是结构债**：第 38 节那条 `key={lastSessionId}` 能修好串台，靠的是「人工记得把状态分桶」；
四段内联分支意味着以后每加一个页面都要再抄一遍同样的闭包依赖。

### 43.1 决定

- 用 **react-router 7**（`HashRouter`；Tauri 下 `tauri://` 与 dev 的 http 都可能，hash 最稳），
  `<Routes>` 里四条 `<Route>`：`/session/:sessionId`、`/repo/:repoId`、`/pr/:repoId/:prNumber`、`/settings`。
- **不再手写路由**（2026-10-30 定）：自维护只换来「零依赖」，参数解析、嵌套布局、守卫、重定向都要自己养，
  而 tab 与路由的对应关系只会越长越复杂。库本身的成本是一次依赖 + 一个 lock 变更。
- **tabs 仍是唯一真源**（它承载 pin / 顺序 / 持久化）。URL 只是它的**投影**：激活项变化时
  `navigate(path, { replace: true })`，**不产生历史条目**（Tauri 没有前进后退语义）。
- 反向（hash → 标签）只在**启动时**读一次，本批**不做**深链，但路由层已经就位。

### 43.2 口径

- 路由路径：`/session/<uiSid>`、`/repo/<repoId>`、`/pr/<repoId>/<number>`、`/settings`（hash router，实际是 `#/…`）。
- **只有 tab → 路径**这一侧是我们要写的纯函数（`pathOfTab`），它必须单测：四种 kind、缺字段（如 pr 没 number）
  返回 `null`、未知 kind 返回 `null`。反向解析归 react-router（`useParams`），不另写一套。
- 路径对不上任何 tab（手改 hash、历史遗留）→ 显示空态（`WorkspaceEmpty`），**不许抛异常、不许自动建标签**。
- 迁移分两阶段，各自一次提交，**行为、样式、文案、事件一行都不许改**（纯搬运）：
  - **B1**：路由 + `RouteOutlet` 骨架 + `repo` / `settings` / `pr` 三块搬进 `src/routes/`（JSX 原样搬，
    props 由 App 组装），App 里删掉那三段内联分支与 PR 骨架块；
  - **B2**：`session` 块搬进 `src/routes/SessionRoute.tsx`，跨层依赖用 **React context**（不引状态库）
    收口；`App.tsx` 只留「状态 + 分派」，目标 **< 2600 行**（3029 行里约 2000 行是状态与 handler 装配，
    搬 JSX 只能减 400 行左右；再往下把逻辑拆成 `useSessionActions` 一类属**独立一轮**，不在 B 里做）。
- 每个阶段都必须 `tsc -b` 过 + 全量 `npm test` 数量不下降；测试数下降按红处理。

### 43.3 验收

- 四个标签来回切：渲染与改动前逐项一致（真机肉眼比对，所有者验收）；
- `location.hash` 跟随激活标签变化，但窗口的「后退」不会改变界面（没有历史条目）；
- 非法 hash（`#/session/`、`#/pr/x`、`#`）不崩、落到空态；
- B2 之后 `App.tsx` 行数 < 1200，`routes/` 下每个文件单一职责。

### 43.4 实测结果（2026-10-30）

- `App.tsx`：3038 → **2813** 行（B1 −120，B2 −225）；`src/routes/` 五个文件共 682 行
  （`SessionRoute` 385 / `workspace-context` 184 / `PrRoute` 72 / `RepoRoute` 33 / `SettingsRoute` 8）。
- **没到 §43.2 写的 < 2600**：直接原因是 `Workspace` 那个 70 字段的对象字面量（72 行）必须留在 App 里做装配。
  再往下压只能把装配逻辑拆成 `useSessionActions` 之类的 hook —— 那是独立一轮，不在 B 里夹带。
  不为了对齐目标行数去改结构，也不改目标糊过去：这就是实测值。
- 逐行核对：原 `session` 块 290 个非空行，在 `SessionRoute.tsx` 里**一行不缺**（脚本比对，缺失 0），
  除缩进外无差异；`App.tsx` 里 `activeTab?.kind === "session"` 已归零。
- 门禁：`tsc -b` 0 / `npm test` 462 pass / `check-i18n` 0-0-0。

## 44. 更新说明（release notes）按 markdown 渲染

**现象**：设置页「发现新版本」下面那块说明，把 `**加粗**`、反引号、`- ` 项目符号原样显示成纯文本 ——
因为它是 `<pre>{notes}</pre>`（`components/UpdateSection.tsx`）。

**事实**：这份说明本来就是 markdown。链路是
`CHANGELOG.md` 的版本段落 → `release.yml` 写成 `.ci/changelog-section.md` →
`latest.json` 的 `notes` 字段 → 更新器 `Update.body` → 前端。v0.0.10 的 notes 实测 404 字符，
含 `**加粗**`、反引号、多条 `- ` 项目符号，且项目符号带缩进续行。

### 44.1 口径

- 用**已有的** `components/Markdown.tsx`（底层 `lib/markdown.ts` 的 `parseMarkdown`，与聊天同一条解析路径、
  同一套 `.sc-prose` 排版）渲染，**不新增依赖、不引第二个 markdown 库**。
- 链接沿用 `Markdown` 内部的 `openExternal`，在系统浏览器打开；不在应用内打开（桌面壳没有浏览器上下文）。
- 容器改成 `max-h-64`（说明比纯文本占地方，`max-h-40` 只够看三行）、内部滚动，保留
  `rounded-mark` / `border-line-1` / `bg-surface-2` / `p-3` / `text-caption` / `text-ink-2` 这套既有样式。
- `notes` 为空照旧不渲染这一整块（不显示空盒子）。

### 44.2 验收

- 设置页检查更新后，说明里的加粗、反引号、项目符号、缩进续行都按 markdown 呈现；
- 点说明里的链接：在系统浏览器打开，应用内不跳走；
- 说明很长时可滚动，区块不撑破设置页。
