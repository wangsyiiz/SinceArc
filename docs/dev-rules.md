# 开发规范（事故驱动）

> 每一条都对应真实踩过的坑。写进这里的目的不是仪式，而是**下次不重犯**。
> 与 `architecture.md` 的不变量一一对应；冲突时以 `architecture.md` 为准。

## 1. 十一条铁律

1. **归属显式**：任何改变状态的操作都带 `uiSessionId`；事件由后端填投递目标。
   禁止用「当前打开的会话」「最近一次操作」推断归属。
   *（事故：切会话时回答写进另一个会话，两个会话的历史互相污染。）*
2. **身份不复用**：消息/轮次/请求的 id 必须唯一且一次性。
   *（事故：回答用 `stream-<acpSessionId>` 作主键，`ON CONFLICT DO UPDATE` 把历史回答整条覆盖。）*
3. **不留空白**：一轮结束必须有终态记录（回答或失败原因），系统提示也要落库。
   *（事故：失败提示只存在内存，恢复会话后是「连着几条提问、一条回答都没有」。）*
4. **库是权威**：历史只从库读；内存只是缓存，切会话必须重读并合并。
   *（事故：内存非空就跳过读库，最后一条回答永远不出现。）*
5. **尺寸实测**：布局留白/弹层位置必须读 `getBoundingClientRect()` / `ResizeObserver`。
   禁止用常数估算高度。
   *（事故：底部留白写死 128px，输入框一高就盖住最后一条消息；弹层按 320px 估高度导致飘移。）*
6. **不假设字符集**：解析用户内容（handle、消息、路径）不得用 `\w` 等 ASCII 类。
   用「已知集合 + 边界」匹配，或按字节/字符长度处理。
   *（事故：`@hermes-测试2` 被 `[\w-]` 截成 `@hermes-`，发送时报「不在群里」。）*
7. **外部输入先验证**：agent 交付的 id/路径/名称一律当不可信输入；不匹配就显式失败，不做模糊兜底。
   *（事故：握手名取第一段匹配不到 codex-acp，能力面板空白。）*
8. **可空 ≠ 可猜**：字段缺失（映射、归属、标题、模式）时按「没有」处理并留痕，
   不构造一个看起来合理的默认值。
9. **破坏性操作要授权**：只删本地记录、一次显式确认、不进回收站、不动 agent 侧产物。
   正在跑一轮的会话禁止删除。
10. **地基不认识业务**：通信层/持久化层/适配器不得包含业务判断（谁属于谁、什么算合法、该怎么排）。
    判断标准：把业务规则拿掉，地基还能编译能跑。详见 `architecture.md` §6.1。
11. **失败要可见**：写库失败、投递失败、解析失败必须在界面或日志留痕；
    `catch` 里只 `console.warn` 等于没有处理。

## 2. 禁用清单（可在 review 时直接对照代码）

- ❌ `lastSessionId` / `activeSession` 参与**数据归属**或落库决策。
- ❌ 固定 id 的消息（`stream-<sid>`、`msg-<sid>`）用于可重复写入。
- ❌ `if (state.msgs.length > 0) return;` 这类「有数据就不再读源」的短路。
- ❌ 前端计算业务量：token/成本估算、命令拼装、权限判定、排序分组落库、成员字段校验规则。
- ❌ 前端硬编码 px 作为布局依据（高度、位置、间距）去避让浮层。
- ❌ 正则字符集解析用户名/短名/命令输出里的标识符。
- ❌ `catch {}` / `.catch(console.warn)` 吞掉持久化或投递错误。
- ❌ 在 `commands.rs` 里内联复杂 SQL，或在 `db/` 里做业务判断。
- ❌ 同一判据在两处实现（前端 + 后端），尤其校验与默认值。
- ❌ 直接用 `<select>`、引入新的 UI 库/依赖；不走 `sc-glass`/`surface-*`/`ink-*` 设计令牌。

## 3. 完成定义（DoD）

一项功能/修复只有在下面全部成立时才算完成：

1. 文档：先有规范（新建或改既有 feature 文档），代码与文档一致。
2. 类型与构建：`tsc -b` 0 错、`vite build` 通过（Windows 侧 node）。
3. Rust：`cargo test --lib` 全绿；`cargo clippy --all-targets -D warnings` 干净。
4. 真机：涉及 ACP 链路的改动必须跑真机测试（`cargo test --test <x> -- --ignored`）。
5. 手工验证清单：在提交信息里写清「看什么、期望什么」，由所有者确认或由日志对账。
6. 日志：新链路有可追溯的 `clog` 打点（发送 / 结果 / 落库 / 丢弃原因）。
7. 回写：规范文档里更新「实现进度」表；行为变更同步 `architecture.md`。

## 4. 验证层级

| 层 | 手段 | 何时必须 |
|---|---|---|
| L0 | `tsc -b` / `vite build` | 每次改前端 |
| L1 | `cargo test --lib`（含不变量单测：路由精确命中、标题生成、消息去重） | 每次改后端 |
| L2 | 真机 `--ignored` 测试（hermes 实机：session/new→load→prompt→chunk） | 改 ACP 链路 |
| L3 | 手工验证清单（见提交信息） | 改交互/布局 |
| L4 | `sincearc.log` 对账（`LOAD db=n live=m`、`SEND/RESULT/DB-OK`、`DROP-*`） | 涉及「消息去哪了」类问题 |

排查「消息丢失/串会话」时的固定顺序：**L4 日志 → L1 单测 → 代码**。不要先猜。

## 5. 自审 12 问（提交前逐条过）

1. 这次改动有没有让「用户正在看哪一页」影响数据？
2. 有没有引入一个可被重复写入的 id？
3. 失败路径是否留下痕迹（库或界面）？
4. 从库里恢复后，界面会不会与库不一致？
5. 有没有用常数代替测量？
6. 有没有假设 ASCII / 字面量格式？
7. 外部给的值是否都当不可信处理？
8. 缺数据时是「没有」还是「猜一个」？
9. 同一条判据是否只在一处？
10. 破坏性操作是否需要用户显式授权？
11. 文档是否已改（或说明为什么不用改）？
12. 提交信息里是否写清「怎么验证、期望看到什么」？

## 6. 日志规范

- 客户端日志走 `clog(tag, text)`（`<app_data>/sincearc.log`）；标签固定：
  `SEND` / `FLUSH` / `RESULT` / `DB-OK` / `DB-ERR` / `FAIL` / `DROP-NOMAP` / `DROP-REPLAY` /
  `RESULT-NOUI` / `PERM-NOUI` / `BIND-NOUI` / `REBIND` / `SALVAGE` / `LOAD` / `RENDER`。
- **不记正文**，只记 id、长度、角色、条数。日志不是对话备份。
- 新链路必须有「成功」和「丢弃原因」两类打点，否则出了问题只能猜。

## 7. 文档规则

- **规范先行**：决策定了先写进文档，再动代码；文档里的判据要能直接转成测试或检查。
- **一个判据只写一处**：同一规则不要同时在 feature 文档和架构文档里各自表述。
- **枚举必须带兜底**：列出的情形之外一律走默认动作（通常是「拒绝/不推/不猜」）。
- **实现进度要标**：feature 文档末尾维护进度表，未做项写清缺什么、卡在哪。

## 8. 改动流程

1. 读相关规范 → 2. 写/改规范（含验证方式）→ 3. 实现（一次一项）→
2. 跑门禁（L0/L1，必要时 L2）→ 5. 回写进度表 → 6. 提交（写清验证清单）。
